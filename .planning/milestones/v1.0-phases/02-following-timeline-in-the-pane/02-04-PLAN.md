<objective>
Build the shell: the one keymap table and its three surfaces, the Bubble Tea v2 model with a real back stack and
an anchor, the status line wired to the live budget, and the composition root that puts the binary on screen.

Purpose: this is the phase's user-visible product — the timeline in the pane — plus the navigation shell that
Phases 4-7 will push through. REND-03, REND-05, REND-06, FEED-01, FEED-04, OPS-01 and OPS-02 all land here,
because all seven are properties of how input, frames, the status line and the wire meet.

Output: `internal/keys`, `internal/tui` (pure `Update`/`View` with every read as a `tea.Cmd`), `internal/cli`'s
failure mapping and `feed` subcommand, and the boundary test that keeps the shell unable to touch I/O.

Phase goal (ROADMAP, quoted): "The user reads their Following timeline in a terminal pane — scrolling back
through older posts and refreshing deliberately — and the pane never lies about what it is showing."
</objective>

**Module fetch note (verified 2026-10-14).** The Go proxy is unreachable directly from this host and works
through the user's Clash proxy: every module-fetching command needs
`HTTPS_PROXY=http://127.0.0.1:7897` and `HTTP_PROXY=http://127.0.0.1:7897`. Add
`charm.land/bubbletea/v2 v2.1.0` to `go.mod` and tidy through that proxy (verified in ~6 s; the transitive set
is 22 modules). Do not use a fetch command without the proxy and do not add a second UI library: the UI-SPEC
pins bubbletea v2 plus `charmbracelet/x/ansi` and explicitly does not use a widget library for the pane, the
status line or the help overlay.

`model.go`:
- `type Deps struct{ Source domain.Source; Budget func() (used, limited int, reset time.Time); Failure func(error, []netcheck.Result) domain.Failure; Now func() time.Time }`.
- `type frame struct{ List screen.List; Anchor int }` — the UI-SPEC's frame: the list kind, the pages loaded,
  the opaque cursor and the selected post id live in `screen.List`; the anchor is the selected block's head row
  distance from the pane's first row.
- `type Model struct` holding the frame stack (`frames []frame`, the top one is what renders), the help-modal
  flag, the terminal size, and the per-process state the UI-SPEC says is not per-frame: the sticky
  `failure domain.Failure`, the refresh notice and the in-flight latch that gates a repeated key.
- `func New(d Deps) Model`: one frame, `ForYou`'s frame absent, `screen.List` for `domain.Following`, and an
  `Init()` returning the first page command (the Following list is the default surface).

`update.go`:
- Every read is a command value. `func (m Model) fetchPage(c domain.Cursor, k domain.HomeKind) tea.Cmd`
  returns a closure that calls `m.deps.Source.Home(context.Background(), k, c)` and returns either a
  `pageMsg{Kind, Page, Cursor}` or a `failureMsg{Err}`. Nothing in `Update` or `View` calls the source.
- Route a result to its frame by `domain.HomeKind`: with two feeds there is at most one frame per kind, and a
  result whose kind has no frame is dropped (it cannot corrupt the visible list). Phase 4 replaces this with
  opaque frame ids and the comment says so.
- Key dispatch: on `tea.KeyPressMsg`, if the help overlay is open then `help` and `back` close it and every
  other action is ignored (no key reaches the list); otherwise `keys.ByKeystroke(msg.Keystroke())`.
- Movement: `next`/`prev`/`half-down`/`half-up`/`page-down`/`page-up`/`first`/`last` move the selection through
  the list's own lookups (`NextID`, `PrevID`, `FirstID`, `LastID`) by the right step over the *rendered* block
  heights (half and full page steps are measured in pane rows, not posts), and adjust the anchor so the
  selected block's head row is inside `[0, paneRows-1]`, clamped.
- Reaching the last loaded post with a stored cursor triggers the next page: `screen.List.Update(
  PageRequested)` returns an effect, which becomes a command; further presses while the latch is set return no
  effect, so a slow page never queues a burst and **the selection does not move until the page arrives**.
- `refresh`: issue `screen.List.Update(RefreshRequested)` only when nothing is in flight — the key is debounced,
  so key-repeat cannot burst requests. The notice (`{n} new posts` / `no new posts`) comes back with the page.
- `toggle-feed`: push a fresh frame for the other feed kind, fetching nothing; pressing it again pops it. The
  restored frame must return byte-identical, so a non-top frame is never mutated: a refresh applies to the top
  frame only.
- `back`: pop a frame, or quit at the bottom frame. `quit`: `tea.Quit`.
- `tea.WindowSizeMsg`: set the size, re-render from the same state and clamp the anchor; no re-fetch and no
  state change other than the clamp (this is REND-03, and `A5` below is its test).
- `failureMsg`: store the failure on the model (sticky until a fetch succeeds; no timer clears it), and gate
  requests: a not-retryable failure blocks page and refresh effects until it is resolved — except the
  rate-limited row, which unblocks once `now >= failure.Reset` — and a stopped failure blocks them for the
  rest of the process.

`view.go`:
- `func (m Model) Render(w, h int) string`: project the top frame and the per-process state into
  `render.Blocks`, `render.StatusFields` (state and remedy from the failure kind, notice from the notice state,
  list from the frame's kind, position from the selection index and the loaded count with the `+` while a next
  cursor is stored, budget from `m.deps.Budget()`), and return `render.Frame(...)`. The shell adds no bytes: the
  frame is exactly what the engine produces.
- `func (m Model) View() tea.View`: `tea.NewView(m.Render(m.w, m.h))` with `AltScreen: true` — the pane is the
  whole terminal, the frame is repainted in full every time and the feed never lands in the terminal's
  scrollback, which is why this is chosen over inline rendering (Phase 3's cover work then has less to clear;
  `MouseMode: tea.MouseModeNone` so mouse reporting is never enabled and the terminal keeps its own selection
  and paste), no `WindowTitle` and no `ProgressBar` (Phase 3 owns the title), and no bell.
- The help modal: while it is open it replaces the pane with `render.Help(...)` built from `keys.Rows()`
  (keys joined by `, `), and the status line stays as it is.

`failure.go` — the one place an error becomes the state the screen shows.
- `func failureFor(err error, check []netcheck.Result) domain.Failure`: map `*xweb.APIError` by its `Outcome`
  (the three renamed classifier rows included), `xweb.ErrRequestCap` to the budget-spent kind,
  `session.ErrNoSession` to the no-session kind, and anything else through the netcheck results: the first
  failed `netcheck.Result` names the path state (no route, proxy refused, upstream blocked, TLS challenge,
  transport unusable) with `Detail` copied from that result's own sentence. Set `Detail` from the classifier
  (`Outcome.Remedy()`) for the API rows, `Reset` from `APIError.Reset` for the rate-limited row, `Retry` false
  for the rows whose remedy is "do not retry" (rate limited before its reset, soft ban, budget spent, bad
  request, endpoint retired) and true otherwise, and `Stopped` only for the soft-ban kind.
- `Detail` is never empty: when nothing better is available, use the classifier's own sentence for an
  unclassified shape, so the pane can never render a failure as a blank line.
- Nothing here re-types a state word: the words live in `internal/render/copy.go` and the kinds are what
  crosses this boundary.

`failure_test.go`: one row per `xweb` outcome asserting the kind mapped and the `Detail` equal to that
outcome's own `Remedy()`; the rate-limited row with and without a `Reset`; the soft-ban row mapping to a
stopped, non-retryable failure; `ErrRequestCap` and `session.ErrNoSession`; a netcheck result set whose first
failure is each of the five path outcomes; and the arm: a test that walks every kind the mapper can produce and
asserts `Detail` is non-empty, so a new error class cannot slip through with nothing to show.

`feed.go` — the composition root and the subcommand, the only place that names the whole stack:
- load the config (`config.Load`), resolve the pins path under the data dir and load the registry
  (`volatile.Load`), load the session (`session.Load`) — a missing session is the no-session *state*, not a
  crash: build the model with the failure already set and issue no request;
- build the transport for the configured proxy, one `*xweb.Limiter` from the config's floor and cap, one
  `*xweb.Client`, and `xsource.New(client)`;
- build `tui.Deps` with `Source`, `Budget: limiter.Budget` (the same limiter every request goes through, so the
  line cannot drift from the requests issued), `Failure: failureFor`, `Now: time.Now`;
- run `tea.NewProgram(model)`; a clean quit exits 0. Register `feed` in `commands()` with a usage line naming it
  as the timeline.
- Any config or registry warning goes to `ctx.Stderr` before the program starts — never into the pane.
