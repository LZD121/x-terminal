**One section per case, in this order, each with a stable anchor** (the doctor's failing lines name these anchors, so the headings must be `## <title>` with the anchor written once as an HTML comment or as the heading's own text):

| Section | The failure it repairs | The built surface it exercises | Its verification command |

**Every section's four parts, in this order and with these names:** `**Symptom.**` — the exact words the status line shows, **quoted from `xweb.Outcome`'s own constants and `domain`'s state words rather than paraphrased** (a paraphrase drifts from the classifier and the reader stops trusting the file); `**What doctor shows.**` — the line or lines of the report for this case, named by their labels; `**Repair.**` — one command or one file edit, with the exact path (the session file, `pins.json`, `saved.db`, `config.toml`); `**Verify.**` — one command from the verification column above, whose output is the answer.

**The repairs, stated as the operations they are** (the fourth part is the one a reader may skim; the third may not):

- Rotation: `doctor --refresh-ids` first because a bundle change is the common cause; if the operation is not in the new bundle either, pin it by hand with `doctor --pin <operation> <query-id>` and say where the id comes from (the operation's own document, the sibling project's snapshot — never from a guess); the pin is read at every start, so no rebuild is needed.
- Features drift: re-run `doctor --refresh-ids` and pin nothing — the feature switches come from the registry, and a stale registry is the whole failure.
- Signer break: confirm the session is not the cause (`doctor`), re-export the session and re-run; then `doctor --refresh-ids`; then `doctor --probe <operation>`. The section says plainly that if all three fail the operation needs a header this build does not send, that this is the one state a reader must stop and report, and it names the file a source change would go in (`internal/xweb/graphql.go`'s request builder) — a runbook that pretended otherwise would be the file's first lie.
- Session expiry: `x-terminal logout` (it deletes the local copy; the browser session is untouched), re-copy the cookie pair from the browser's own storage into the session file, re-run `doctor`; the section quotes `session.Load`'s mode check (a file anyone can read is a failure, not a state).
- 429: read the reset instant off the status line or `doctor --probe`, wait for it, then one probe. No retry, no loop, no second attempt.
- Soft ban: stop for the session; the section says explicitly that a soft ban with budget remaining is the upstream holding the account back for reasons this client cannot see, so waiting for a reset is not the remedy.
- The mirror: an owner mismatch is repaired by moving the file aside (`mv saved.db saved.db.old`) and syncing fresh — the store refuses to re-point a mirror, and that refusal is a feature: the file is one account's. A newer schema is repaired by updating the build or by moving the file aside if its contents are expendable, and the section says which of the two loses data. An unreadable file is repaired by the same move-aside.
- The likes endpoint: pin the operation if the id is known; otherwise the section says the mirror is still worth having with bookmarks alone, and `doctor --probe Likes` is how the user finds out which case they are in.
- Accidental distribution: unpublish or archive the artifact; rotate the credential (log out everywhere, or change the password — the session cookie is a bearer token for the whole account); re-read what the terms say about internal endpoints; then re-run `audit` and the leak sweep. A repair instruction, not a policy essay — the project's position on distribution lives in `PROJECT.md`, and this section points at it rather than repeating it.
- The short sections: one paragraph each, the repair being "do not retry" (endpoint retired, unclassified) or "wait and probe once" (load shed, empty body), with the verification named.

Avoid: a section without a built command in its verify part; a symptom paraphrased rather than quoted; a repair that needs a code change presented as a configuration step; a second copy of `PROJECT.md`'s policy; prose where a command belongs.
