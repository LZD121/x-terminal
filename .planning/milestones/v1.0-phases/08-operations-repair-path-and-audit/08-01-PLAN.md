<objective>
Land the phase's audits as a package and a verb: `internal/audit` with one pure check per promise the project makes — read-only, no mutation expressible, no timers, one persistence file, no distribution artifact or hosted mode, one account, the cookie sweep, and the import boundaries — plus `x-terminal audit`, which prints what each check inspected and exits non-zero when anything is found.

Purpose: SEC-03's "no write call anywhere in the build" is a property of the tree, not of intent, and the phase's own rule is that a check must be able to fail. Every check therefore reports the number of files it inspected (a scan of nothing passes every negative assertion ever written), has an anti-vacuity arm, and has a deliberate-failure proof both as a permanent test with a synthetic violation and as a planted violation in the real tree that is observed failing and reverted.

Output: `internal/audit` and its tests, the extended `internal/session` leak surface list, the `audit` verb and its test, and the one new row in the command table.

Requirement ownership: SEC-03 is this plan's `requirements` entry (the repo-wide proof that no write call exists, and the cookie sweep re-run that keeps it honest). OPS-03 (the extended doctor) is plan 02's; OPS-06 (the runbook) is plan 03's.

**`internal/audit/audit.go` — the shape every check shares.**

- `type File struct { Path string; Src []byte }` (Path relative to the repository root, `/`-separated), `type Tree []File` with `func Load(root string) (Tree, error)`: every non-test `.go` file of the module plus the few manifests a check needs (the module files, the registry JSON as data, any workflow or packaging file that happens to exist — the walk is over a declared list of globs, and a check may ask for a subset). Test files are excluded from the tree the checks scan, deliberately and with a comment saying why: a test is allowed to name the thing it drives.
- `type Finding struct { Check, Path, Detail string; Line int }` (Line 0 when the finding is about the file as a whole), `type Report struct { Check, Promise string; Files int; Findings []Finding }`, and `type Check struct { Name, Promise string; Run func(Tree) Report }` with `Run` filling `Files` from the tree it was handed.
- `func Checks() []Check` and `func Run(root string) ([]Report, error)`: load once, run every check, return the reports in a fixed order. A check that panics is caught and becomes a finding — an audit that dies with a panic has audited nothing.
- Package doc comment: the package reads files and nothing else — no `internal/store`, no `internal/xweb`, no shell, no process — so that a broken build can still be audited; and it never prints a post body, a token or a path outside the repository, because its report is the thing a user pastes when something is wrong.

**`internal/audit/readonly.go` — promise 1 and 2.**

- `operationNames(t Tree)`: parse every non-test Go file with `go/parser` (the same technique `internal/tui/boundary_test.go` already uses for imports) and collect every string literal that looks like a GraphQL operation name: any literal that either appears in the registry's own operation-name set (read from `internal/xweb/volatile/registry.json`, which is **data** and exempt — it carries the whole bundle's map, writes included, and pruning it would violate XAPI-03's add-only refresh rule) or appears in this package's own write-name table. Record file and line for each.
- `opClass`: the classification table, in this file, one row per name: `read` for every operation the build may name, `write` for the names that mutate an account (the post, reply, like, repost, follow and bookmark write operations — spell them out as the table's rows). Any collected name the table does not classify is a finding ("unclassified operation name: is this a read or a write?"), any name classified `write` is a finding, and an empty collected set is a finding (the anti-vacuity arm, with the count printed). The check's doc comment says plainly what it can and cannot see: it scans names the code *spells*, so a name assembled at run time from the registry is not visible to it — which is exactly why the transport check below exists.
- `transport(t Tree)`: no request carries a method other than GET — match the standard library's method constants and any `"METHOD"`-shaped literal in a request-construction position — and no file outside `internal/xweb` builds an `*http.Request` (match the constructors). Both arms carry the count of files inspected.
- `readonly_test.go`, with hand-written sources in `audit/testdata/` and the trees built in memory: a table of reads passes; a name outside the table fails with its file and line; a write name fails; an empty tree fails; a tree whose only literals are unrelated strings fails the anti-vacuity arm; a non-GET method fails; a request built outside `internal/xweb` fails; and the real tree passes.

**`internal/audit/guards.go` — promises 3 to 6 and the boundaries.**

- `timers(t Tree)`: in non-test source, no periodic-timer constructor, no one-shot timer, no after-func, no tick channel and no sleep call — the only permitted wait is the limiter's own inter-request floor, and the check names that one file and line as its exemption (so the exemption is visible and counted, not silent). Each banned call is a finding with the token, the file and the line. Anti-vacuity: the check reports how many files it parsed and fails if the exemption it expects (`internal/xweb/limiter.go`'s floor) is absent — a tree with no limiter is not a tree this check proved anything about.
- `persistence(t Tree)`: every write-capable call site (the create/open/write calls and any store DSN string) resolves to exactly one of the four allowed destinations: the session file's create-if-absent template, `pins.json`, the first-run marker, and `saved.db` with its `-wal`/`-shm` siblings. The check prints the destinations it found with their files and lines, and fails on a fifth. Anti-vacuity: it fails when it found fewer than the four expected destinations (a scan that missed one has proved nothing about the fifth).
- `distribution(t Tree)`: no container file, no package recipe, no release configuration, no install or release script and no publishing workflow exists in the repository (a declared list of file-name patterns, matched against the walk's file list), and no listener, server or bind-address construct exists in the source. The check's comment says why: the project's scope says it is not distributed and has no hosted mode, and this is where that stops being a sentence.
- `account(t Tree)`: exactly one session-path resolution (the config package's `SessionPath` and the session loader) and exactly one credential pair exist — one place that reads the two cookie names — and no per-account flag or per-account config key is declared. Anti-vacuity: the check fails when it finds zero session-path resolutions (a build with no session path is not a build with one account).
- `boundaries(t Tree)`: `internal/tui` reaches none of the network, process, database or lower-layer packages it may not import, and the volatile vocabulary (the query-id field name, the feature-switch names and the bundle hosts) appears only under `internal/xweb/volatile`. This re-asserts Phase 2's and Phase 7's boundary tests from the tree-wide side; the plan records that the two must both be able to fail, and that either failing is a finding.

**`internal/audit/leak.go` — promise 7, the sweep re-run.**

- One fixture cookie, one captured surface list: the doctor's text report and its JSON twin, the sync verb's output, the audit's own report, the media notices (the phase-7 strings), the store's error strings, and a recovered panic's output. Each surface is produced through the code that produces it today (a doctor run with a stubbed check, a sync run with a fake fetcher, the audit's own report, a rendered media notice, a store error built with a bad path, and a `recover()`ed panic printed) — nothing is searched as a string literal in a source file, because the promise is about output.
- The concatenation is searched for the cookie, with the two arms `internal/session/leak_test.go` established: the search must find the cookie in a control string that contains it (so a broken search cannot pass), and the surfaces must be non-empty.
- `internal/session/leak_test.go` grows its surface list rather than being replaced: the doctor's new lines (plan 02's) and the audit's own report are added to the same test so the sweep has one owner and one fixture.

**Tests.** `guards_test.go` and `leak_test.go`: for every check, a synthetic violating tree produces a finding naming the file and line and a clean tree does not; each check's anti-vacuity arm fires on the empty or partial tree; the sweep finds nothing in the real surfaces and does find the fixture in its own control string.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the tree → the report | the audit reads a repository and prints a report a user pastes somewhere; nothing it reads may leak out with it |
| the audit → the guarantee | a scan that inspects nothing, or that cannot fail, converts a promise into a green line — the failure mode worse than no scan |
| the verb → the repair path | `audit` is a step a user runs when something already went wrong, so a crash or a stack trace there is a second failure on top of the first |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Information disclosure | `internal/audit/leak.go` and the report | high | mitigate | The sweep is the check that the audit does not leak what it scans; the report carries paths relative to the repository and bounded sentences, and the verb's test asserts no absolute prefix and no token in its output |
| T-08-02 | Repudiation | the checks themselves | high | mitigate | Every check reports the number of files it inspected, has an anti-vacuity arm, a synthetic-violation test and a planted-violation observation recorded in the SUMMARY; a check that cannot fail is treated as a finding about the audit |
| T-08-03 | Denial of service | a panicking check | low | mitigate | A panic inside a check is recovered and becomes a finding, so the verb always prints a report and an exit code |
| T-08-04 | Tampering | the tree the audit reads | medium | accept | The audit reads the working tree as data; a user who edits the tree is the same user the audit is for, and a build that cannot be audited is reported rather than bypassed |
| T-08-SC | Tampering | module installs | high | mitigate | This plan adds no module: the audit package uses the standard library's parser and file walking only, and `go.mod` is unchanged |
