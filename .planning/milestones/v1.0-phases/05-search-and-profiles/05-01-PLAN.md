<objective>
Open the search surface: a query prompt opened by `/`, and a results list that is Phase 2's list — same blocks, same
walk, same keys — carrying the `latest` and `top` products of the `SearchTimeline` operation.

Purpose: DISC-01's keyword search with its explicit Latest/Top toggle. It lands first because the results list is
where the phase's premise is first visible: the frame is a `Walk[domain.Post, domain.PostPage]` exactly as the home
timeline is, with no second cache, cursor, dedupe set or stall rule; and because the search response is the one body
this phase reads whose shape is not yet recorded in the repository, so the decoder and its fixture are its critical
path.

Output: `domain.SearchProduct` and the port's `Search`; `xsource/search.go` + a captured, redacted fixture + its
provenance; `fake/search.go`; the prompt and the results frame in `internal/screen`; the prompt row, the status
labels, the two notices and the `MarkerSet` fields in `internal/render`; two keymap rows; the prompt modal, the
search frame kind and the zero-request `esc` in `internal/tui`.

Not in this plan: people (`u` and the account row — 05-03), the profile (05-02), the stored golden corpus (05-03),
and any refresh of the search frame beyond Phase 2's rule reused as-is (task 3).

Requests (bounded, and each one named): opening the prompt spends 0; submitting a query costs exactly 1
`SearchTimeline` request (the query, the page count, the product, the cursor); `s` from a `latest` frame costs
exactly 1 `SearchTimeline` request under `top` (a pushed frame), `s` from a `top` frame costs 0 (a pop), and `s`
anywhere else costs 0 and says `nothing to switch`; reaching the last loaded result costs exactly 1 `SearchTimeline`
request at the stored cursor — single-flight, and a repeated cursor ends the walk; `r` costs exactly 1
`SearchTimeline` request for page one under the same query and product.
+
`esc`, a selection move, a page already in flight and every prompt keystroke cost 0.

Phase goal (ROADMAP, quoted): "The user searches posts by keyword and finds people, then reads a profile's bio and
recent posts through the same list they already know."

Coordination note (stated, not hidden). Phase 4's plans are being written in parallel and are not on disk at the
time of this plan; Phase 4's planner has stated its split (received 2026-10-14): `internal/screen/walk.go` holds
`Target{ID, Path}` and `Walk[T, P]` with `NewWalk[T,P](idOf func(T) string)`, the sealed `Request` union
(`Request` cases carried on `Effect.Req`), and `Effect{Kind, Req, Cursor, Head}`. This plan names those shapes and
extends them in place — one walk, one cursor type, one stack. If Phase 4's landed shape differs, the executor
adapts to it and never forks it.

Key resolution (stated). `05-CONTEXT.md` describes the product cycle on `t` and one prompt; `05-UI-SPEC.md` fixes
two entry points (`/` for posts, `u` for people) and `s` as the Latest/Top toggle, and `04-UI-SPEC.md` narrows the
`t` row (`switch-list`) to screens `home`. The UI-SPEC is this phase's design authority: this plan adds `/` and `s`,
05-03 adds `u`, and `t` is left exactly as Phase 4 lands it.
</objective>
