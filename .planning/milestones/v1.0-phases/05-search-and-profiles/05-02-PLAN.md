<objective>
Open the profile: `a` on a selected post reads the author's header and page one of their posts, and the pane shows the
header — identity, bio, counts, join date — above the account's posts, which page on the same walk the timeline uses.

Purpose: DISC-03. It lands after the search plan and before the people list because it is the one surface of this
phase that needs no new list machinery to be reached (`a` works from the timeline, a thread frame or a search frame
alike), and because the people list's rows are only useful once a row can be opened into this frame (05-03). The two
requests are the whole cost of a profile and the reason the header exists as a value: `UserTweets` addresses an
account by its numeric id, which only the header returns.

Output: `domain.Profile` and the port's `Profile`/`UserPosts`; `xsource/profile.go` with a captured header and
matched posts fixture; `fake/profile.go`; the profile frame reducer; the header block and the facts line in
`internal/render`; the `a` row; the profile frame kind and the two-request open in `internal/tui`.

Not in this plan: the user row and the `u` entry point (05-03), the stored golden frames (05-03), replies/media tabs
(`UserTweetsAndReplies`, `UserMedia`), the pinned post, and any change to `domain.User`.

Requests (bounded, and each one named): `a` on a selected post costs exactly 2 — `UserByScreenName` for the header,
then `UserTweets` for page one, addressed by the numeric id the header returned — and a header failure costs 1 and
issues no second request; `a` on a row with no author, and `a` where the author is already the top frame's profile,
cost 0; reaching the last loaded post costs exactly 1 `UserTweets` request at the stored cursor (single-flight, and a
repeated cursor ends the walk); `r` costs exactly 2 (`UserByScreenName` then `UserTweets` page one) and a second `r`
while the pair is in flight costs 0; `esc`/`q` cost 0.

Content decision (stated, because two artifacts disagree). `05-CONTEXT.md` says the profile fields are fields
`domain.User` gains; `05-UI-SPEC.md` — this phase's design authority — says `domain.User` is not edited and
`Profile` holds the user plus the header facts the screen prints. Follow the UI-SPEC: `Profile` carries
`{User, Bio, Followers, Following, Posts, Joined}` and nothing else, `domain.User` stays the post author's shape, and
no verification field is carried (the UI-SPEC's Content table names none, and no grammar this phase ships prints
one).

Coordination note (stated, not hidden). Phase 4's plans are not on disk at the time of this plan; this plan uses the
shapes 04-UI-SPEC.md fixes and Phase 4's planner has stated (`Walk[T, P]`, `Target{ID, Path}`, the sealed `Request`
union on `Effect.Req`, opaque frame ids) and extends them in place. 05-01 already added the composed `list` field and
the `SearchRequest` case; this plan adds two more cases to that same union and no walk of its own.
</objective>

`internal/domain/profile.go`: `Profile` = the account (`User`) plus the facts the header prints — `Bio string`,
`Followers, Following, Posts *int`, `Joined time.Time`. The counts are POINTERS on purpose: "absent" and "zero" are
different facts and the screen prints them differently (`absent values are omitted, never zeroed`). Add the port's
two methods to `internal/domain/source.go` in Phase 2's `Home` shape:
`Profile(ctx context.Context, handle string) (Profile, error)` — one account's header, no pagination — and
`UserPosts(ctx context.Context, id string, c Cursor) (PostPage, error)` — one page of one account's recent posts,
addressed by the numeric id the header returned, empty cursor for page one.

`internal/screen/profile.go`: the profile frame, built the way `internal/screen/search.go` is (one walk, no state of
its own beyond the frame's own facts):

- `type Profile struct` carrying the handle, the header (`domain.Profile` + whether it arrived), the walk
  (`Walk[domain.Post, domain.PostPage]`) and the request pair this frame issues; the page cache, the cursor, the
  dedupe set, the stall flag, the single-flight latch, the failure, the selection and the anchor are the walk's.
- `Open(handle string) (Profile, Effect)` returns the frame and the FIRST effect only: the header request.
- `Update(ev Event, now time.Time) (Profile, Effect)`: `HeaderFetched{Header domain.Profile}` stores the header and
  returns the SECOND effect (page one of that account's posts at the header's own `User.ID`), so the two requests
  are ordered by the frame's state and not by the shell's convenience; `HeaderFailed{Failure}` records the failure
  and issues nothing further (a failed header spends one request, never two); `PostsFetched{Page domain.PostPage}`,
  `PostsFailed{Failure}`, `RefreshRequested{}` and `Refreshed{Page domain.PostPage}` translate into the walk's
  operations as 05-01's frame does. A repeated event while a request is in flight is the walk's no-op, unchanged.
- `Refresh` state: the profile's `r` is the header request and then page one, in that order — the frame records
  which of the two the refresh is waiting on, so a second `r` while the pair is in flight spends nothing, and the
  posts' prepend-only diff is the walk's `RefreshPrepend` behaviour 05-01 reused for search.

`internal/screen/walk.go`: add the `ProfileRequest{Handle string}` and `UserPostsRequest{ID string, Cursor
domain.Cursor}` cases to the sealed `Request` union. Nothing else changes there.

`internal/render/profile.go`: `ProfileHeader(p domain.Profile, g Grammar, w int) Block` — three kinds of row, in
order, all at the frame's content origin: the identity row from the `UserHead` template
(`{handle:16} {name}` — the same template 05-03's user row uses, defined once here), the bio wrapped at the measure
with EVERY line printed, and the facts row: the clauses in the fixed order `followers: {n}`, `following: {n}`,
`posts: {n}`, `joined: {Month Year}`, separated by two spaces, each clause omitted when its value is absent, and the
row itself omitted when no clause survives. `Profile(p domain.Profile, posts []domain.Post, g Grammar, w int,
sel Selection, now time.Time) []Block` returns the frame's one block list: the header block, one blank separator
row, then the posts' blocks — the separator is the render layer's rule (Phase 2's), never the shell's.
