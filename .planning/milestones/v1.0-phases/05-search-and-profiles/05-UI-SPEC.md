# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This document extends `.planning/phases/02-following-timeline-in-the-pane/02-UI-SPEC.md`
("Phase 2"), `.planning/phases/03-three-state-disguise-on-the-working-renderer/03-UI-SPEC.md`
("Phase 3") and `.planning/phases/04-post-detail-threads-and-quotes/04-UI-SPEC.md` ("Phase 4"), and
does not restate them.** Phase 2's grid, post block, block separator, width model, colour roles and
ladder, status line and its drop order, keymap table, back stack copy policy and golden-frame method
are inherited unchanged; Phase 3's `Grammar`/cover seam (`Head`/`QuoteHead`/`MarkerPlace`/
`PaneHeader`/`BodyIndent`/`BodyPrefix`/`MeasureCap`/`Separator`/`Stamp`/`Identity`/`Ref`/`Markers`/
`ShowCounts`, the `CoverAlias` projections, the `{stamp}`/`{ref}`/`{handle}`/`{name}`/`{email}`/
`{markers}`/`{state}`/`{text}` placeholders, the covered copy set, the `HelpCovered` row field and
the panic state machine) is the vocabulary every seam below is written in; Phase 4's thread frame,
its `Target` selection, its `screens` row field and its `Walk[T]` are inherited the same way. Every
deviation is marked *deviation* with its reason; every inference is marked `[INFERENCE]`.

This spec also resolves two places where the phase's own `.planning/phases/05-search-and-profiles/
05-CONTEXT.md` and `04-CONTEXT.md` disagree; both are named in place, and neither is silently picked.

## Design System

| Property | Value |
|----------|-------|
| Tool | `none` — no CSS design system; a Go terminal program (inherited) |
| Preset | not applicable |
| Component library | `charm.land/bubbletea/v2` v2.1.0 (runtime only) + `charmbracelet/x/ansi` v0.11.9 (SGR, width) — no widget library (inherited) |

| Font | the terminal's own monospace cell; the program sets no font, size, weight or line height (inherited) |

**What this phase adds to the package split** (file names are `05-CONTEXT.md`'s, so that parallel
phases do not collide):

| File | Ownership this phase adds |
|------|---------------------------|
| `internal/xsource/search.go`, `internal/xsource/profile.go` | the `SearchTimeline` decoder for both entity kinds (posts and accounts) and the `UserByScreenName` + `UserTweets` decoders behind the profile. |
| `internal/domain/profile.go` | `Profile` (the user plus the header facts the screen prints), `SearchProduct`, and the port this phase's screens consume. |

| `internal/render/user.go`, `internal/render/profile.go` | the user row and the profile header block; every literal added to `copy.go`, with the covered spelling beside it in `copy.go`'s covered set (Phase 3's mechanism). |
| `internal/fake/search.go`, `internal/fake/profile.go` | fixture-backed sources in their own files, rather than growing the shared fake. |
| `internal/keys` | four rows (`/`, `u`, `s`, `a`) and their `HelpCovered` texts. |

- **Every user-visible string this phase adds is a named constant** — the plain one in
  `internal/render/copy.go`, the covered one in the covered copy set Phase 3 established
  (`cover.go`). A reviewer must be able to read this phase's entire visible output in those files,
  and no site builds a sentence by concatenation outside a grammar template.
- **No registry, no third-party design assets** (inherited): nothing is fetched, installed or
  themed at runtime. **No text-input widget**: the prompt is one row rendered by `internal/render`
  and edited by the shell, in the same spirit as Phase 2's decision to render the pane rather than
  use `bubbles`.
- **The new operations are registry entries, not literals.** `SearchTimeline`, `UserByScreenName`
  and `UserTweets` are named in `internal/xweb/volatile`'s registry and pinned snapshot like every
  other operation (`XAPI-02`/`XAPI-03`): no `queryId` string appears anywhere else in the
  repository, and a refresh may only add or update an entry, never drop one. The `product` variable
  is content (`SearchProduct`), never a screen string.
- **No new id type.** The walk keys a row by a plain string supplied by the element (a post id, an
  account id); nothing above the port parses an id (`05-CONTEXT.md`'s rule; it is why Phase 4's
  `Target.ID` is a `string`).
- **Both surfaces are the same walk.** This phase is where Phase 2's claim that the list was
  extracted entity-agnostically is *proved*: a user result is a row in the same list state — same
  selection, same scrolling, same pagination, same failure handling, same back stack — see
  `### The Entity-Agnostic Seam`.

## Typography

Inherited unchanged: one cell, one row per line, exactly one text attribute (reverse video on the
selected rows), no bold, no underline, no second weight, no heading role (`REND-01`).

- The display name is a new *field* on a head row, not a new *role*: same cell, same weight, no
  larger type, no capitals, no underline. It appears in a user row and in the profile header's
  identity row, and nowhere else in the program (`04-CONTEXT.md`'s resolution, carried here).
- The profile's facts line is metadata, not a stat row: one row, same cell, no bold, no boxes, no
  glyph, no animation. The words (`followers`, `following`, `posts`, `joined`) carry the meaning, so
  no symbol is needed to say "these are numbers about an account".
- The focal point of a profile frame is, in order: (1) the selected rows, (2) the identity row
  (handle then display name), (3) the post blocks below. The header never out-emphasises a post.

## Copywriting Contract

Phase 2's and Phase 3's tables stand. The rows below are this phase's additions; each has a covered
spelling in Phase 3's covered copy set, and a covered frame may contain none of the plain literals.

| Element | Copy |
|---------|------|
| Prompt, posts product (`/`) | `search: latest` then two spaces then the typed text |
| Prompt, people product (`u`) | `people:` then two spaces then the typed text |
| Status line, `list` field, posts search | `search: latest "{query}"` / `search: top "{query}"` (the query quoted, as `05-CONTEXT.md` specifies) |
| Status line, `list` field, people search | `people: "{query}"` |
| Status line, `list` field, profile | `profile: {handle}` `[INFERENCE]` — `05-CONTEXT.md` fixes the two search forms and says nothing about the profile's; this keeps the same shape |
| Empty search result (successful read, zero rows) | `no results` **in the `notice` field** — not a pane heading (`05-CONTEXT.md`'s decision) |
| Empty profile post list (successful read, zero posts) | `no posts` in the `notice` field `[INFERENCE]` by the same rule; the header is still on screen, so the pane is not empty |
| Loading, search frame's first page (pane statement) | `loading results...` |
| Loading, profile header (pane statement) | `loading profile...` |
| Loading, the profile's first post page (`notice`, the header already on screen) | `loading posts` |
- Pagination is Phase 2's and Phase 4's, unchanged: reaching the last loaded row asks for the next
  page, single-flight, the selection does not move until it arrives, a stall ends the walk
  (`no older posts (cursor stalled)`), and dedupe is id-keyed. The `position` field counts rows
  (posts or accounts) and carries `+` while a next cursor is stored.

- **The query is never written anywhere** (`05-CONTEXT.md`): it lives in the frame and in the
  status line's `list` field, so no search history, no cache, no config key exists. The echo is
  capped at 32 cells, cut at a cluster boundary with `~` in its last cell; the field is droppable in
  Phase 2's order, so the query can be off screen, and `/` re-seeds the prompt with the frame's own
  query — that is the recovery path.
- **`no results` / `no posts` are deliberate deviations from Phase 2's pane-headed empty state**
  (`no posts in following` + a body row): `05-CONTEXT.md` puts a search's empty state in the
  `notice` field, in the successful state, and requires that no failure ever render as an empty
  list. The pane is then empty (or, for a profile, holds the header) and the words are in the one
  line that always exists.
- **A user row has no placeholder strings.** An account with no display name prints nothing where
  the name would be; an empty field is not an error and gets no word.

## Screen Grammar

### The prompt (both entry points, one modal)

`/` opens the query prompt for posts; `u` opens the same prompt for people. Both work from every
frame (`/` and `u` are `all`). `[INFERENCE]` this two-entry-point shape and the pane-modal mechanics
follow `05-CONTEXT.md`; it supersedes the single-prompt-plus-product-cycle this document carried
before that file landed.

- **Mechanics are Phase 2's help overlay's.** The prompt replaces the **pane**, the status line
  stays exactly as it was (so the request budget is on screen the whole time), no frame is pushed,
  no request is issued, and `esc` closes it and restores the pane with nothing changed.
- **It states the product before the request is paid for**, which is the whole reason it exists:
  the row reads `search: latest ` + the typed text, or `people: ` + the typed text. The product is
  never discovered afterwards.
- The prompt row is the pane's first row; the pane's remaining rows are blank (emitted, as always,
  so the frame is `H`×`W`). The row obeys column 1 = the selection column like every other row, and
  it carries no `>` (nothing is selected while the prompt is open).
- **The caret is the terminal's own cursor, never a byte of the frame** — the shell computes one
  cell (row 1, column `Width(prefix) + Width(visible text) + 1`, clamped to `W`) and Bubble Tea
  places it. Golden frames therefore stay byte-comparable and `TERM=dumb` still works. *Deviation
  with a cost, stated:* this is the **only** place the program positions the cursor; Phase 2 kept
  the cursor out of the render layer ("the render layer never does arithmetic on a cursor"), and
  there is no honest text field without a caret.
- **Editing is deliberately minimal**: printable runes insert, `backspace` deletes one cluster,
  `ctrl+w` deletes the last word, `ctrl+u` clears the row, `enter` submits, `esc` cancels. A paste
  containing newlines is normalized to single spaces (the field is one row). `enter` on an empty
  query does nothing and the prompt stays open.
- **While the prompt is open, every printable key is text**, including `?`, `/`, `u`, `s` and `a`;
  the keymap table is shadowed except for those five keys and the four editing keys. A text field
  that treated `?` as a command would be unusable, and this is the one place in the program where a
  printable key is not a command.
- A query longer than the row shows its **tail** (so the caret stays visible); the query is measured
  by `internal/text` like everything else, so a CJK or emoji query measures correctly.

### The search frame

A search frame is `{the query, the product, the walk, the selected target, the anchor}` and the
product is one of:

| Product | Reached by | What the list holds | Row shape |
|---------|-----------|---------------------|-----------|
| `latest` (the default for `/`) | `/` → a query | posts, in the order x.com returned them | Phase 2's post block |
| `top` | `s` from a `latest` frame with the same query | posts, as x.com ranks them | Phase 2's post block |
| `people` | `u` → a query | accounts | the user row (below) |

- **`s` is the Latest/Top toggle, and it is a frame toggle, not an in-place rerun**: from a
  `latest` results frame it pushes a `top` frame **for the same query** (one request, shown in the
  budget line), and pressing `s` on a frame that was opened that way pops it, so the frame it
  returns to has kept its rows because non-top frames are frozen. This is Phase 2's `toggle-feed`
  semantics exactly, which is what makes `q`/`esc` and the back stack mean the same thing on every
  screen. Pressing `s` where there is no order to switch — a home, thread, profile or `people`
  frame — prints `nothing to switch` in the `notice` field and issues no request
  (`04-CONTEXT.md`'s "applies only when…" rule).
- **The results render as the timeline's blocks do**: same grammar, same width model, same cover,
  same markers, same quote nesting, same tombstone/limited/withheld literals. The search adds **no
  decoration**: no rank numbers, no highlighted matched term (`A2-S`), no result count, no spinner,
  no "search mode" banner. The word in the status field is the only signal.
- An empty result set prints `no results` in the `notice` field in the successful state and is
  never rendered as a failure; a failure never renders as an empty list (`NET-03`).
- Pagination is Phase 2's and Phase 4's, unchanged: reaching the last loaded row asks for the next
  page, single-flight, the selection does not move until it arrives, a stall ends the walk
  (`no older posts (cursor stalled)`), and dedupe is id-keyed. The `position` field
  counts rows (posts or accounts) and carries `+` while a next cursor is stored.
- **Homogeneity, as a property.** A list is one entity kind by construction: the product decides it
  and a page never mixes kinds, so a row carries no type word — the status field names the product
  and the row's own shape says the rest. A test asserts no stored frame contains both a post block
  and a user row.
- `enter` opens whatever the selected row *is*: a post's conversation (Phase 4's thread frame) or an
  account's profile. `a` opens the author of the selected post (`## Keymap Contract`).

### The user row

```
>lzd              Maria
```

- **One row per person** — `05-CONTEXT.md`'s decision, and it supersedes the two-row form (handle +
  name + bio) this document carried before that file landed. A directory entry, not a profile card.
- **Head row:** `{handle:16} {name}`, the same shape as Phase 2's post head row with the display
  name where a post's stamp would be. There is no stamp: an account has no post time. The handle is
  left-padded to exactly 16 cells (no `@` sigil, Phase 2's rule, 20 under Phase 3's covers); the
  display name is truncated so that the row's content — handle field, one space, name — is at most
  `measure` cells, with `~` in the last cell it may occupy (`name ≤ measure - 17`).
- **Not printed:** no bio, no follower/following/post counts, no verification glyph or word, no
  avatar or banner, no location, no website, no join date, no "follows you" marker. Counts in a list
  are exactly what Phase 2 removed, and `DISC-03`'s counts belong to the profile header.
  *Named compromise:* telling two accounts with the same display name apart costs one keystroke
  (`enter` to read the profile, its facts and its posts) instead of a number in the list, and the
  bio — the most useful discriminator — is one screen away. That is the price of a people list that
  reads as a directory rather than a directory of social profiles.
- The row is selectable; the `>` margin and reverse video mark it like any other target; `enter` and
  `a` both open its profile.

### The profile frame

`{the header block, then the account's recent posts}` — one list, the same machinery, the same keys.

**Two requests, in this order** (`05-CONTEXT.md`): the header (`UserByScreenName`), then page one of
the posts (`UserTweets`, addressed by the numeric id the header returned).

| State | Pane | Status line |
|-------|------|-------------|
| header in flight | `loading profile...` (a head-shaped statement, no header yet) | Phase 2's fields for the frame underneath, budget included |
| header arrived, first post page in flight | the header block, then nothing | `notice`: `loading posts` |
| header arrived, posts arrived | the header block, a blank row, the post blocks | Phase 2's fields |
| header arrived, posts failed | the header block stays; the failure is on the status line (`FEED-05`'s rule) | the state's own `state` + `remedy` |

**The header block.** Three kinds of row, in this order, all at the frame's content origin; the
whole block is *not* selectable (there is nothing to open inside an account's own profile):

| # | Row | Layout |
|---|-----|--------|
| 1 | identity | `{handle:16} {name}` — the user row's head row exactly; no stamp |
| 2 | bio | the body indent, the bio wrapped to the measure, **all lines** (this is where the bio is read) |
| 3 | facts | the body indent, one row of `key: value` clauses separated by two spaces: `followers: 1204  following: 312  posts: 8901  joined: Mar 2011` |

- **Absent values are omitted, never zeroed.** Each clause is its own template; a clause whose
  value the answer did not carry is not printed (never `followers: 0`), and if no clause survives,
  the row is not printed at all. A missing bio prints nothing — no placeholder, and no empty row.
- *Deviation, stated:* `05-CONTEXT.md`'s decisions call this "one line of plain `key: value` text"
  while its specifics ask for "one fact per line, aligned". This document takes the decisions'
  reading — one line of clauses — because four extra header rows would be a quarter of a 24-row
  pane for facts, and this phase's own rule is that the header must not become chrome. The clauses
  are `key: value` (a database record's shape, per the specifics) with no glyph, no colour beyond
  the muted role, and no alignment padding.

**The header must not become chrome.** It is a block of the list, and it is prohibited from being:
pinned, sticky, repeated or re-drawn while the list scrolls; a box, a rule, a border, a background
or an alternating fill; a titled or labelled region (`PROFILE`), a banner, an avatar, or a
decorative glyph; a second status line — nothing about the account is repeated in the status row
beyond the `list` field's `profile: {handle}`.

Also deliberately absent: the account's **website** (Phase 2 removed printed URLs from the surface
and Phase 7 owns links; the upstream value is a `t.co` redirect, which is exactly the kind of text
this program refuses to print), its **location** (not in `DISC-03`), a **pinned-post marker** (the
pinned post is deferred — it is a row that is not part of the walk and can duplicate one that is),
and the account's **verification**: read from the response but printed by no grammar this phase
ships, because a badge is an icon wearing a word and the handle, the display name and the facts are
the honest discriminators.

**Reading the header again.** One blank row separates the header block from the first post block
(Phase 2's separator). The header scrolls away with the list and is never re-drawn; `g`/`home` —
whose help text stays `first loaded post`, which is still exactly true — returns the view to the
frame's first row, so the header is always one key away. `[INFERENCE]` that this is consistent with
Phase 2's anchor clamp (the offset is 0 at the frame's top and the header is simply the first block
there); the planner should assert both frames (`g` from a scrolled position, and a cold frame).

**The posts below.** The account's recent posts are ordinary Phase 2 blocks in the answer's order
(UserTweets only; the replies and media tabs are out of scope). Pagination is the same implicit
trigger; `r` re-reads the profile (header and page one) and prepends only unseen post ids,
announcing `{n} new posts` or `no new posts` — Phase 2's refresh rule verbatim, because this list is
the same kind of list. The `position` field counts posts: a freshly opened profile shows `1/240+`,
the header being no part of the count.

### What is deliberately absent from these surfaces

Inherited from Phase 2 and confirmed: no avatars, no icons or emoji decorations, no engagement
counts in a list, no rules, boxes or alternating backgrounds, no printed URLs, no relative times, no
numbering, no heading row, no colour-carried meaning.

Specifically for this phase: **no counts in a list** (only the profile header prints numbers about
an account, because `DISC-03` requires them there, and it prints them as one plain facts line); **no
bio in a user row**; **no highlighting of the matched term** (`A2-S`); **no "no results for: …"
repetition** (the status field names the query); **no search history, saved searches, suggestions or
autocomplete**; **no spinner or progress animation** (Phase 2's loading statements are statements,
and the program has no timer); **no advanced search operators**, no `from:`/`filter:` syntax, no
"search this thread's author" action.

## The Status Line

Phase 2's row, order, separator rule and drop order stand. **This phase adds no field and changes
no drop order** — stated explicitly:

```
{state}  {remedy}  {notice}  {list}  {position}  {budget}
```

Drop order when the line does not fit `W`: `notice`, then `position`, then `list`; `state`,
`remedy` and `budget` are never dropped. One left-aligned run, no right-aligned segment.

| Field | Value in these frames |
|-------|----------------------|
| `list` | `search: latest "{query}"` / `search: top "{query}"` / `people: "{query}"` / `profile: {handle}`; the query is capped at 32 cells, `~` in the last cell |
| `notice` | Phase 2's vocabulary (`loading older posts`, `no older posts (cursor stalled)`, `{n} new posts`, `no new posts`), plus `no results`, `no posts`, `loading posts`, `nothing to switch`, `no author to open` |
| `position` | unchanged format; counts rows (posts or accounts) for a search frame, posts for a profile frame (the header is not counted), plus `+` while a next cursor is stored |
| `state`, `remedy` | Phase 2's closed state table, unextended: a failed search or profile read is one of the classes already there |
| `budget` | unchanged, and present in **every** frame this phase renders, including the prompt (which is why the prompt is a pane modal: a status-row prompt would hide the budget — a rejected alternative, recorded) |

## Width Model

Phase 2's model stands in full (`Width`/`Wrap`/`Pad`/`Truncate` in `internal/text`, the `$TMUX`
dispatch, no second measurement, `A4`–`A7`), as do Phase 3's grammar-adjusted measure and Phase 4's
reply-level term. Additions:

| Element | Rule |
|---------|------|
| user row head | the handle field is exactly 16 cells; the display name is truncated so the row's content is at most `measure`; `~` in the last cell the name may occupy |
| profile header bio | every line wrapped to the measure; no truncation (the profile shows the whole bio) |
| facts line | one row; a clause wider than the row is truncated with `~` at the measure (it never is in practice: three numbers and a date) |
| query echo | at most 32 cells in the `list` field, cut at a cluster boundary with `~` |
| prompt row | `Width(prefix)` plus the visible text; when it exceeds `W` the **tail** of the text is shown and the caret column is computed from what is shown |
| prompt caret | always within `1..W`, for every prefix/query pair, including wide clusters |

`A4` is extended: for every fixture string and every `w` in `{1, 2, 3, 5, 8, 55, 77, 96}`, the
wrap/pad/truncate properties hold for a display name, a bio, a facts clause and a query echo.

## Keymap Contract

Phase 2's table stands, with Phase 3's rows (`m`, `c`, `1`–`4`, `ctrl+p`), Phase 3's `HelpCovered`
field and Phase 4's `screens` field and `enter` row. **This phase adds four rows:**

| Keys | Action | Help text (rendered verbatim) | Group | Screens |
|------|--------|-------------------------------|-------|---------|
| `/` | `search-posts` | `search posts` | feed | all |
| `u` | `search-people` | `find people` | feed | all |
| `s` | `search-order` | `search order: latest / top` | feed | all |
| `a` | `open-author` | `open the selected post's author` | navigate | all |

- `/` and `u` open the same prompt with different products (`### The prompt`); neither issues a
  request until `enter`.
- `s` toggles a posts-results frame between `latest` and `top` by pushing/popping (Phase 2's
  `toggle-feed` semantics, `### The search frame`), and where there is no order to switch it prints
  `nothing to switch` in the `notice` field and issues no request. `[INFERENCE]` the `all` screens
  value: `05-CONTEXT.md` says `s` "reports 'nothing to switch' elsewhere", which is `04-CONTEXT.md`'s
  "applicable key whose action has nothing to act on reports one honest line" — so the row is
  applicable everywhere and the line is its answer, rather than being silently inapplicable.
- `a` opens the selected post's author's profile: from any frame holding a selected post, including
  a search result, a thread row and a profile's own posts. Where the selected row has no author
  (a tombstone or withheld post with no author in the content value) it prints `no author to open` in
  the `notice` field; where the author is already the top frame's profile it is a no-op (pushing a
  duplicate frame would add a back-stack step that returns to the same screen — `[INFERENCE]`,
  extending `04-CONTEXT.md`'s rule that opening the current frame's own focal post is a no-op).
- `enter` is Phase 4's row and dispatches on the selected row's kind: a post → its conversation, an
  account → its profile. That one dispatch is the entity-agnostic list paying off.
- **Collisions with Phase 3 are resolved in Phase 3's favour**, as `04-CONTEXT.md` and
  `05-CONTEXT.md` both state: Phase 3 lands first and its state keys work in every state. Phase 3's
  landed allocation (`m`, `c`, `1`–`4`, `ctrl+p`) collides with none of this phase's four rows;
  **if the plan finds a collision against the keymap as it actually landed, the row here moves.**
- **In panic, the table is shadowed** (Phase 3's T10): only `ctrl+p` and `ctrl+c` act, so `/`, `u`,
  `s` and `a` are swallowed there like everything else. Nothing in this phase changes that.
- **The prompt's keys are not table rows** (`enter`, `esc`, `backspace`, `ctrl+w`, `ctrl+u`, plus
  the "every printable key is text" rule): the prompt is a modal over one row, exactly as `?`-help is
  a modal over the pane. Adding them to the table would document five keys that do nothing in every
  list frame.
- **Every new row carries both help texts** — the plain one above and a `HelpCovered` one, since
  the `?` overlay works under a cover (Phase 3's rule); the covered wordings are Phase 3's to word,
  and no covered row may name a product.
- The `keys` subcommand's output stays `keys<TAB>action<TAB>help`, three fields, in table order:
  a listing subcommand has no frame context (Phase 4's rule).
- Back stack: `/` and `u` push nothing; the prompt pushes nothing; `s` pushes/pops one frame.
  `enter` and `a` push a thread or a profile frame. Popping returns byte-identically with zero new
  requests (Phase 2's four observables). A search frame's contents are `{query, product, the walk,
  the selected target, the anchor}`; a profile frame's are `{handle, the profile value, the walk,
  the selected target, the anchor}`.

## Content / Presentation Split

Phase 2's split stands: content owns what is true about a post or an account; presentation owns
every character the user sees; no `domain` value holds a rendered string.

### Content this phase adds (`internal/domain/profile.go`, produced by `internal/xsource`)

| Content field | Upstream path (the new schema, as Phase 1's fixture carries it) |
|---------------|------------------------------------------------------------------|
| `Profile.User` | the account, as `domain.User` already models it (`core.name`, `core.screen_name`, `rest_id`) |
| `Profile.Bio string` | `profile_bio.description` |
| `Profile.Followers int` | `relationship_counts.followers` |
| `Profile.Following int` | `relationship_counts.following` |
| `Profile.Posts int` | `tweet_counts.tweets` |
| `Profile.Joined time.Time` | `core.created_at` — the **account's** creation instant (`Tue Feb 20 14:35:54 +0000 2007`), which is the join date; parsed in `xsource`, never a string above it |
| `SearchProduct` | the operation's `product` variable: `Latest`, `Top`, `People` |

**`domain.User` is not edited** (`05-CONTEXT.md`): it is the post author's shape and stays that way.
`Profile` holds the user plus the header facts the screen prints and nothing else — no website, no
location, no banner, no verification flag, no pinned-post id.

The port this phase's screens consume is declared beside them and implemented by the adapter:

```go
// internal/domain
// Search returns one page of a post search. The product decides the ranking: Latest is
// reverse-chronological, Top is x.com's. An empty cursor asks for page one.
Search(ctx context.Context, query string, p SearchProduct, c Cursor) (PostPage, error)
// SearchPeople returns one page of accounts matching the query. [INFERENCE] a method of
// its own: 05-CONTEXT.md names the consumers' vocabulary (Search, Profile, UserPosts) and
// leaves the People walk's shape to this phase, and a page of accounts is not a PostPage.
SearchPeople(ctx context.Context, query string, c Cursor) (UserPage, error)
// Profile returns one account's header: bio, counts, join instant.
Profile(ctx context.Context, handle string) (Profile, error)
// UserPosts returns one page of one account's recent posts, addressed by the numeric id
// the header returned.
UserPosts(ctx context.Context, id string, c Cursor) (PostPage, error)
```

`UserPage{Rows []User, Next Cursor, Requested int, FetchedAt time.Time}` mirrors `PostPage`'s shape;
nothing about the wire crosses the port — no `product` string, no cursor type, no `sortIndex`.

### Presentation this phase adds (`internal/render`)

In Phase 3's vocabulary, and nothing more:

| Field | Value in `Plain` | What it decides |
|-------|------------------|-----------------|
| `UserHead []string` | `["{handle:16} {name}"]` | the user row's and the profile header's identity row: one template, so a cover can render its own directory form (`{ref}`/`{handle:20}`/`{name}`) with no code change |

### The Entity-Agnostic Seam

`DISC-02` is the requirement that proves Phase 2's list was extracted entity-agnostically, so the
seam is part of this contract. Phase 4 lands it (`internal/screen/walk.go`) as one implementation
parameterized by the element type; this phase instantiates it twice and adds no machinery:

```go
// internal/screen — Phase 4's; this phase adds the Request cases and instantiates it.
// Walk is one list's state: the page cache, the id-keyed dedupe set, the opaque cursor, the
// stall flag, the single-flight latch, the failure, the selected Target and the anchor. It is
// parameterized by the element (a post, an account) and by the page value the loader returns,
// and it keys every element by the string id the element supplies — there is no id type here
// and nothing above the port parses one.
type Walk[T any, P any] struct { /* … */ }
```

| Kind | What it is |
|------|-----------|
| **Entity-blind (shared, never forked)** | the page cache, id-keyed dedupe, the opaque cursor, stall detection, the single-flight latch, the failure, the selected `Target`, the anchor, and the scroll/selection arithmetic |
| **Entity-aware (per frame, three things)** | the page loader (which port method and arguments), the row renderer (Phase 2's post block, or the user row), and the status field's words |

- **A user result flows through the list view, not through a parallel one**
  (`05-CONTEXT.md`): a People page is `Walk[domain.User]`, and a search page and a profile's posts
  are `Walk[domain.Post]` exactly as the home timeline is. A second pagination path, a second dedupe
  set or a second stall rule is a defect, not an alternative.
- **Entities are distinct in rendering and identical in behaviour**: a user row is not a post block
  and is not forced into one; the pane dispatches on the row kind, which is the frame's kind.
- **Homogeneity holds by construction**: a `Walk` is monomorphic, so a list cannot mix an account
  and a post, and the "no type word on a row" rule needs no exception. A test asserts no stored
  frame contains both forms.
- **Parallel safety, stated for the planner:** `internal/screen/walk.go` is shared with Phase 4
  (which creates it) and Phase 6 (which adds saved rows). This phase adds `Request` cases and
  instantiates the walk; it does not change its shape. If Phase 4's landed shape differs from the
  sketch above, this phase extends it in place — the rule from both context files is *one
  implementation of the walk, extended in place, never a second one*.

### Through the cover (DSGT-08)

Both surfaces are expressible through Phase 3's `Grammar`/cover seam; nothing needs a second
renderer, and the costs are named:

| Element | Carried by | A cover supplies |
|---------|-----------|------------------|
| the handle (user row, header, status field) | `Grammar.Identity` → `CoverAlias.Handle` | nothing new |
| the display name | `{name}` → `CoverAlias.Name` | nothing: the alias already makes it safe, and a cover that does not want a name-shaped field edits `UserHead` |
| the facts line | `AccountFacts` + `Stamp.MonthYear` | `nil`, or its own clauses (a service log might render `records={posts}`) — a cover printing `followers=1204` would be its own tell (`DSGT-09`) |
| the bio, the posts | body text and Phase 2's block layout through Phase 3's `Head`/`BodyIndent`/`BodyPrefix`/`Markers` | Phase 3's alias rule must also rewrite mention runs inside a bio and a post body — `[INFERENCE]` that `Post.Text`/`Profile.Bio` are plain strings in the current `domain`, in which case the alias function parses the handles out of the text; Phase 3's frame scan is the test |
| the user row's and the header's shape | `UserHead`, `Markers.UserRow` | its own templates |
| the statements (`no results`, `loading results...`, …) | `Markers.*` plus the covered copy set Phase 3 established | its own lines |
| the prompt's prefix | `Markers.PromptSearch` / `Markers.PromptPeople` | `filter:` / `people:`-equivalent wording of its own |
| the search frame's product, the walk, the back stack | the screen values and the shell | nothing |

`Markers.PromptSearch`/`PromptPeople` are markers rather than constants precisely so a cover can
rename the prompt without a code change; they and the new statements are the **one thing this phase
must add in two places** (the plain literals and the covered set), which is the whole cost of
`DSGT-08` for these two surfaces.
