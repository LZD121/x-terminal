<objective>
Make every claim this phase makes falsifiable: store the covered and panic frames as the phase's view
specification, scan those bytes for the identities they must not contain, prove the panic round trip and the
write order at the model's own level, and measure the clear in a real terminal and a real multiplexer with a
control run.

Purpose: the phase's promises are all negative or exactness claims — nothing of the account on screen, nothing
of the feed left behind, the same screen back — and each one is only as good as the test that fails when it
breaks. This plan is that set of tests.

Output: the covered and panic golden frames with their audit, the shell-level end-to-end tests, and the
scrollback harness in both environments.

Requirement: DSGT-08 is this plan's `requirements` entry — the whole surface that exists working under a cover
with unchanged keys, which is what the counterpart comparison below asserts.

Phase goal (ROADMAP, quoted): "The user can wear the feed as work-software output or replace the pane with a
one-key panic frame — identities aliased, nothing on screen naming the real product — and step back without
losing their place."
</objective>

The names, in the UI-SPEC's own spelling: `cover_servicelog_80`, `cover_servicelog_120`, `cover_gitlog_80`,
`cover_gitlog_120`, `cover_ci_80`, `cover_ci_120`, `cover_internal_80`, `cover_internal_120`, `panic_80`,

The covered list names are longer than the plain ones, so the covered frames must show the drop rule doing its

`corpus_test.go` — the audit reads the stored bytes, never a fresh render:

- **The identity scan.** For every covered frame and both panic frames: none of the fixture's handles, none of
  its display names, no hostname of the upstream, no product name, no product noun (`following`, `for you`,
  `post`, `timeline`, `feed`), case-insensitively after stripping SGR — **and** each frame contains at least one
  expected alias (the alias the fixture's account is known to map to by the alias function's own worked
  examples), so a frame that came out empty or truncated cannot pass. Scan the frame that was built *from* the
  fixture for the strings the fixture actually carries: the assertion is "these exact real identities are
  absent", not "the mapping was trusted".
- **The panic frame's own absences.** Both panic frames carry zero ESC bytes, and neither contains any
  substring of the corpus's feed text (the fixture's bodies are the haystack, so the check cannot pass
  vacuously).
- **The copies.** Each covered frame carries its style's own list name and its style's markers, and no covered
  frame carries the plain list names; the panic frames carry no status line at all (their last row is the
  frame's own).
- **The widths.** Every row of every stored covered and panic frame measures exactly `W` cells through
  `internal/text`, and no row's text exceeds `min(W-1, the grammar's measure)` where a body line is concerned.
- **Arms**: the audit asserts the stored corpus holds at least the number of files this table generates (a
  deleted frame fails), asserts the scan ran over a frame that contains at least one selected block and one
  alias, and asserts the panic frames' byte-equality across their widths for the lines the frame draws.

Also add the cross-run stability leg the alias promise needs: a small hand-written pin table (testdata, never
written by the program) holding a handful of account-id → alias pairs from the UI-SPEC's worked examples, which
the test asserts the function reproduces; combined with the stored frames it is what makes "the same account
keeps the same alias across sessions and restarts" a check rather than a hope.

Avoid: regenerating a frame inside an assertion; comparing a frame to itself; a second golden harness; letting a
scan pass over an empty frame; and editing the plain frames.

**`cover_e2e_test.go`** — the model-level proofs, driven through the shell's own `Update` and `Render` with the
fake source and a recording terminal port:

- `TestPanicRoundTripIsExact` (the phase's central claim). Build a loaded model in each non-panic state (plain
  and each of the four covers), walk it to a non-trivial place (a selection that is not the first block, a
  scrolled anchor, more than one frame on the stack after a feed toggle, a failure state on the status line, a
  page in flight), then: capture the frame, the source's call count, the frame-stack depth, the selected post
  id, the anchor, the in-flight latch and the failure state; send the panic key; assert the rendered frame is
  the panic frame and that the entry command was dispatched once; send the panic key again; and assert every
  captured fact is identical — the frame **byte for byte**, the call count numerically equal, the stack depth,
  the selection, the anchor, the latch and the failure state all the ones captured. A second leg delivers a page
  answer *while panicked* and asserts it is absorbed (the list behind the overlay gains it) without a frame
  change until the overlay is left, which is what "panic swallows no event" means.
- `TestPanicEntryOrderAndBranches` (the write order, as the UI-SPEC's V6 asks): a recording writer is the sink's
  output and a recording runner is its process runner; entering panic writes the frame's cells before ED 3 and
  ED 3 before the title, exactly one write carries them, and the runner is called after that write; the
  table-driven branch cases follow — an unset pane variable, an empty one and a pane id; a start-up panic (the
  configured state is panic) runs the same sequence after the first frame, not before it.
- `TestTheWholeSurfaceUnderACover` (the plan's requirement): for every state Phase 2's stored corpus names —
  the timeline, the empty read, the loading frame, the help overlay, the four failure states, the stalled
  cursor — render the plain frame and the covered frame from the same model, run the same key sequence against
  both (a movement, a half page, a refresh, the feed toggle, the overlay, `q`/`esc`), and assert the request
  counts are equal and the two plain frames after the sequence are byte-identical; then assert `t`,`t` and
  `ctrl+p`,`ctrl+p` each return the frame they started from byte for byte. The covered frame's *difference* from
  its plain twin must be exactly the grammar and the cover field: nothing else may differ.
- `TestTheTitleIsAFunctionOfTheState`: the table of the UI-SPEC's title column — the plain reader's name, each
  style's own name, the panic frame's name — asserted on the view the shell returns and on the window-name call
  the state's transition asks for, with the arm that no covered title contains a product name.
- `TestNoAliasTableOnDisk` (the privacy promise, asserted where it matters): point the config and data paths at
  a temporary directory, snapshot both directory trees (names, sizes, contents), run a full covered session
  through the real wiring — the four styles, a style switch, a panic round trip, a restart of the model from
  the same config — then snapshot again and assert no file was created or modified except the config file, and
  that its only changes are the two documented display lines. Then grep every file in both trees for the
  fixture's aliases *and* its handles: an alias→handle mapping anywhere fails the test. The config writer is
  driven through the same closure the composition root passes, so a second write path cannot hide.

**`state_test.go`** — extend the transition table with the persist assertions' other half: `m` writes
`display.state`; `c` and `1`–`4` write both keys; a full blur → panic → focus cycle leaves the config file
**byte-identical** to what it was before, which is the involuntary-transition rule asserted as bytes rather than
as a call count.

**`alias_test.go`** — the cross-process leg: run the alias function in a second process (the test binary
re-executed in a helper mode, or a tiny program built in a temporary directory) over the fixture ids and assert
it prints the same aliases the in-process call and the stored pin table hold. This is the "across sessions and
restarts" claim made of two processes rather than one.

Avoid: asserting the round trip by comparing two freshly rendered frames computed the same way (render the
second one from the model as it stands, and compare it to the bytes captured before the panic); a round-trip
test whose model has one frame and one block, which cannot see a stack or an anchor bug; writing anything into
the repository's real config or data directory; and treating the request count as an assumption instead of
reading it from the fake.

  <action>
Write the harness the probe's own method establishes, then hand the one leg that needs a real window to the
user.

The multiplexer leg (`tmux capture-pane -S -N`), runnable from a script: create a detached session at a fixed
size, flood the pane with uniquely labelled lines a fixture can never produce
(`PANIC-LABEL-<n>`), let the program paint a cover, panic, then read the pane's history with
`capture-pane -p -S -5000` and assert no label survives; kill the session in a deferred cleanup so a failing
assertion cannot leave one behind. The **control** is part of the same test and is not optional: the same
flood with the clear disabled (the entry written without its ED 3 sequence and the tmux subprocess skipped —
a switch the test owns, not a code path the program has) must leak the labels, which is what makes the first
result a measurement rather than a no-op. Assert the argument the clear is given is the pane the program was
actually started in, and that with an empty pane variable the harness still runs the bare leg and the entry is
still written.

The bare-terminal leg needs a real window: a fixed-size PTY is not enough, because the question is what the
window shows after injected scroll-up keystrokes and what the window's own capture contains. Write the leg the
way the probe did — inject the scroll-up keystrokes, capture the window, assert no labelled line is visible and
the cover is — and gate it on the environment the probe used (the terminal program and the absence of a
multiplexer) with a skip that prints why, so a run on another machine cannot pass by doing nothing. The
program's panic key can be delivered by the harness's injected keystrokes for this leg, which is also the
end-to-end exercise of the key itself.

Record, in the harness's own comment and in the SUMMARY, what was **not** measurable here and why: a terminal
that ignores ED 3 cannot be detected (there is no portable query, and a query would add a round trip to the
frame that matters most), so the pane keeps whatever was there and the user's recourse is running under tmux,
where the clear is a command with a status; and under tmux focus events reach a pane only when the server's
`focus-events` option is on, which the app deliberately does not change. `tmux show -g focus-events` on this
host is the recorded value. Neither limitation is faked on screen: nothing claims the clear succeeded, and
`ctrl+p` covers the same need by hand.
