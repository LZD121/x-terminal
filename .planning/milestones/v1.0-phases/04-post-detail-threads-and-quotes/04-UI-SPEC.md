## Typography

Inherited unchanged: one cell, one row per line, exactly one text attribute in the whole surface
(reverse video, `SGR 7`, on the selected rows), no bold, no underline, no second weight, no heading
role (a heading is a banner, `REND-01`).

- Emphasis in a conversation is carried by **column position and literal marks** only: the reply
  step (column), the `>` selection cell (glyph), and the words `focal`, `continued` and
  `reply to {handle}`. Nothing in the thread frame is emphasised that is not emphasised in the
  timeline.
- The focal point of a thread frame is, in order: (1) the selected rows, (2) the `focal` marker on
  the post the frame was opened on, (3) the fixed 16-cell identity column. Nothing else competes.

## Color

Inherited unchanged, including the rung ladder, `NO_COLOR` / `TERM=dumb`, and assertions **A1**,
**A2**, **A3**. This phase introduces **no new colour role and no new value**:

| Role | Use in this phase |
|------|-------------------|
| Dominant | post text, handles — including the focal post's text and every ancestor's and reply's text |
| Secondary (`muted`) | stamps, every marker (`focal`, `continued`, `reply to {handle}`, `limited`, `reposted by {handle}`, `post unavailable`, `post withheld`, `post text missing`) and **every pane statement** (`loading thread...`, `no replies`, the three `partial thread - …` lines) |
| Accent (`state` / `state-stop`) | the status line's state word only — not the focal marker, not the partial-thread line |
| Selection | `SGR 7`, the selected target's rows |

**Accent reserved for:** the state word of the status line, and nothing else — confirmed, not
extended. The `partial thread - …` line is deliberately **muted and not accented**: it is a
statement of fact, not a failure state, and the accent is the status line's alone (`A1` still

**Testable assertions, addenda.**

- **A1-T — no meaning by colour alone in a conversation.** Strip every SGR sequence from the
  thread frames and the frame must still unambiguously name the focal post (`focal`), each reply
  relation (`reply to {handle}`, `continued`), the visibility case (`limited`, `post unavailable`,
  `post withheld`) and the partial-thread condition (the statement's own words). Test: render each
  thread golden frame at rung `truecolor` and at rung `mono`, `ansi.Strip` both, compare — the two
  stripped frames must be byte-identical (Phase 2's `A1`, applied to the new frames).
- **A2-T — the thread's state is a literal.** Every condition in `### "partial thread"` renders its
  own words, and no thread frame contains a bare symbol or an empty row where a statement belongs.

## Screen Grammar

### What the thread frame is, and what it is not

**There is no separate "post detail" frame.** The conversation frame *is* the detail view: the
post the user opened, the chain it answers, and the replies under it, in one top-to-bottom list.
ROADMAP groups "Post Detail, Threads and Quotes" because they are one surface; splitting a
post-only frame out would add a second block shape, a second back-stack step and a second set of
golden frames for no reading benefit. `[INFERENCE]` this reading of the phase goal; the ROADMAP's
success criterion ("opening a post reads the focal post and its reply thread page by page") is
satisfied by one frame.

*Deviation from Phase 2's parenthetical.* Phase 2's `### The post block` says display names "appear
in the post-detail header (Phase 4)". There is no such header: the focal post is an ordinary
block, its head row is the ordinary `{handle:16} {stamp:12}` row, and **display names are printed
in exactly one place in the program, Phase 5's profile header**. Phase 2's stored frames and tests
are unaffected (no frame contains a display name either way). Reason: a display name is the main
carrier of decoration and impersonation, and a header existing only to print one would be a second
block shape; the profile header is where identity is the subject. When Phase 2's UI-SPEC is next
touched, that clause should be amended to point here.

### The block order of a conversation

The frame is one list of blocks, laid out top to bottom. Rows, in order:

| # | Part | Source | Indent | Notes |
|---|------|--------|--------|-------|
| 1 | **the chain above** — ancestors, root first, parent last | the answer's own ancestor order | 0 | each ancestor is a normal block; a tombstone among them keeps its place |
| 2 | **the focal post** | the answer | 0 | head row carries `focal`; the selection starts here |
| 3 | **the focal post's own continuations** (the response's self-thread posts) | the answer's own group order | 0 | each carries `continued`; no separator row between the focal block and them, per Phase 2's continuation rule |
| 4 | **the replies** | the answer's own reply-module order, one block per post | one reply step (2 cells) | the reply section; no re-sorting, no tree is derived |
| 5 | **pane statements** — `no replies` + its body row, or one `partial thread - …` line | this phase | 0 for the chain-above statement (it sits directly above the focal block, preceded by one blank row), one reply step for the reply-section statements | not selectable, never a post |

- **No leading separator** before the first block; one blank row **between** blocks (Phase 2's
  rule), dropped between the focal post and its continuations, and never after the last row.
- **Empty parts never render as gaps**: a conversation with no ancestors starts at the focal post;
  one with no replies prints the `no replies` statement.
- Blocks are content-ordered. The frame never reorders what the answer carried, and it never
  re-derives parentage into a tree: the reply group is the answer's own ranked list (`[INFERENCE]`
  from the `TweetDetail` module shape — a group carries a flat post list and its own "show more"
  cursor; if the payload turns out to carry a nested tree, the indent rule below must be revisited,
  but the depth bound and the measure stay safe either way).

### Indentation, depth and the measure

Two facts fix the depth, and both are structural rather than heuristic:

1. **The reply level is 0 or 1.** Everything in the chain above and the focal post renders at 0;
   everything in the reply group renders at exactly one reply step. The indent is a *section*
   marker, not a computed tree depth. This is deliberate: the reply group arrives as a flat ranked
   list, and computing a tree from `ReplyTo` would both reorder the answer and misrepresent replies
   whose parents are not in the frame.
2. **The quote level is capped at 2** (Phase 2's `Markers.QuoteDepthCap`), and a quote nests inside
   a reply by adding its prefix at the reply's own origin.

So the deepest row in any thread frame is a quote inside a reply: `ReplyIndent` + 2 × quote prefix
= at most 3 prefix steps = **6 cells**, independent of how long the conversation is. In Phase 3's
terms the body measure gains one term and nothing else changes:

```
measure = min(W - 1 - BodyIndent - 2*min(quoteLevel, QuoteDepthCap) - len(BodyPrefix)
              - ReplyIndent*replyLevel, MeasureCap)
```

with `replyLevel ∈ {0,1}` and `quoteLevel` counted from the block's own origin; the plain grammar's
values (`BodyIndent` 2, `BodyPrefix` empty) reproduce Phase 2's `min(W - 3 - 2·depth, 96)` exactly.
At the 60-column floor the reply measure is 55 cells, so the measure can never be swallowed; a
renderer that indents by conversation depth instead of by section would produce a 40-deep thread
whose measure collapses, and the golden frames must therefore contain a reply of a reply of a
reply to make that visible (see `### Golden Frames`).

`[INFERENCE]` the reply step of 2 cells and its reuse of Phase 2's `sm` token: a 1-cell indent is
visually accidental, and 4 cells would cost the measure on narrow panes.

### The selection, and what it can land on

Phase 2's rule stands — the selection is never a row index — but the value it holds is widened:

```go
// internal/screen
// Target is the row the cursor is on: the row's own identity as a plain string, plus the
// chain of containing posts when that row is a post quoted inside another post. Empty Path
// is a top-level row. A frame's rows are all one kind (a page never mixes entity kinds), so
// a target is only ever compared with targets of the same frame.
//
// ID is a string, not a new id type: the walk keys a row by the string the element supplies
// (a post id, an account id) and nothing above the port parses one (05-CONTEXT.md's rule).
type Target struct {
    ID   string    // a domain.PostID, converted at the port
    Path []string  // outermost containing post first; empty at top level
}
```

- **The selectable order is the frame's row order**: each block, then that block's quote chain in
  row order (`post → its quote → the quote's quote`). `j`/`k`, `ctrl+d`/`ctrl+u`, `pgdown`/`pgup`,
  `g`/`G` walk that sequence; `Path` is what makes the same post quoted in two places two distinct
  targets, and it is the key the back stack restores.
- The `>` selection cell and reverse video mark the **selected target's rows only**. A quote inside
  a selected block therefore renders `>` in column 1 *followed by* its own `> ` prefix
  (`>> lzd …`) — that is the selection column plus the quote prefix, not a second quote level.
- The status line's `position` field counts **posts (blocks)**, and reports the index of the block
  the selection is inside. Stepping into a quoted post does not change the number: the number
  answers "which post am I in", not "which row". This is why Phase 2's stored position numbers do
  not move when a list gains quotes.
- `enter` on a top-level post pushes that post's conversation; `enter` on a quoted post pushes the
  *quote's* conversation (`THRD-02`), whose own chain above is the post that quotes it. Opening a
  post that is already the top frame's focal post is a no-op, and there is no artificial depth cap
  and no cycle guard: the user can only descend into something they selected, the stack is a slice,
  and the request budget is what bounds the walk (`04-CONTEXT.md`).
- *Deviation with a cost, stated:* Phase 2's `List` stored a bare `domain.PostID` and its accessors
  returned it. This phase changes that field and those accessors to `Target`, and Phase 3's grid
  invariant "the selection is a post id, never a row index" is superseded by *a `Target`, never a
  row index*. The cost is one reducer refactor in `internal/screen` (already landed) plus its tests;
  the benefit is that quotes are openable from every list, not just from a thread. Phase 2's stored
  frames are unaffected: no Phase 2 golden frame has the cursor on a quote.

### The walk, extracted here

Phase 2's `List` is a *post* list whose machinery is element-specific: it absorbs `[]domain.Post`,
keys on a `PostID` and its effect names a home feed. The thread needs the same machinery for a reply
stream, and Phases 5 and 6 need it for accounts, search results and saved items — so **this phase
extracts it once** into `internal/screen/walk.go` as `Walk[T]`, parameterized by the element (a
post here; an account in Phase 5) and by the page value, keyed by the string id the element
supplies:

```go
// internal/screen/walk.go — one list's state, shared by every frame in the product.
// The page cache, the id-keyed dedupe set, the opaque cursor, the stall flag, the
// single-flight latch, the failure, the selected Target and the anchor live here, once.
type Walk[T any, P any] struct { /* … */ }
```

- **Never a second implementation.** A fork of the dedupe set, the stall rule, the single-flight
  latch or the refresh diff is a defect, not an alternative (`04-CONTEXT.md` and `05-CONTEXT.md`
  both state this rule from their own side). This phase instantiates `Walk[domain.Post]`; Phase 5
  instantiates `Walk[domain.User]` and adds its `Request` cases; Phase 6 adds its rows.
- The thread's frame reducer is Phase 2's list state *plus* its thread flags (the focal post's id,
  the partial-thread flags, the reply-stream cursor) — flags beside the walk, not a walk of their
  own.
- **Parallel safety, stated for the planner:** `walk.go` is the one file in the fan-out that is not
  append-only. Whichever of Phases 4–7 executes first lands its shape and freezes it; the others
  extend it in place.

### On push: where the frame opens

**Opening a post costs no request of its own.** The frame renders from the copy the caller already
holds — the selected list row, or the parent's nested quote — so opening is instant and cannot fail;
the first `TweetDetail` page then carries the same post in full and replaces that copy
(`04-CONTEXT.md`; there is no `Post()`/`TweetResultByRestId` read in this phase, so the N+1
anti-pattern is not reintroduced one level up). If that first page fails, the held copy stays on
screen and the failure goes to the status line — a cold-start failure is the same state, never an
empty conversation.

One rule for where the frame opens, deterministic and testable: **the frame opens at its first row
when the focal post's head row is inside the pane at that offset; otherwise the focal post's head
row is the pane's first row.** The selection is always the focal post, so the selected rows are
always on screen when the frame appears. Nothing above the fold is announced by anything but the
position field (`2/6+` — there is a post above the one you opened) and the `focal` marker.
`[INFERENCE]` this is consistent with Phase 2's anchor clamp; the planner should assert both cases
as golden frames.

### The four relationships inside a conversation

Phase 2's relationship table still tells four cases apart by words. Inside a conversation the same
four cases plus two new ones must be tellable apart:

| Case | How it renders | Why it cannot be confused with the others |
|------|----------------|-------------------------------------------|
| ancestor | a normal block at indent 0, above the focal block | its position plus the absence of any marker; the focal marker always sits below it |
| focal post | a normal block at indent 0 whose head row carries `focal` | exactly one block per frame carries `focal` |
| continuation (self-thread) | the focal post's own continuations at indent 0, each with `continued`, no separator above | Phase 2's directional rule, unchanged: it means "answers the block directly above, same author" |
| reply | any block at the reply step (2 cells), in the answer's ranked order | the *section* indent, which no ancestor has; the `>` glyph marks a quote, so an empty indent cannot be read as one |
| reply to elsewhere | a reply whose parent is neither the focal post nor the block directly above it carries `reply to {handle}` | an explicit word, not an inferred depth: the frame never claims a tree it does not have |
| quoted post (inside any block) | Phase 2's `> ` prefix per level, capped at 2 levels | unchanged from Phase 2, including the cap that stops the prefix growing while the text stays intact |

The reply group is the answer's **ranked** list, and the frame claims nothing about that order:
there is no per-group heading and no standing disclaimer. *Named compromise:* a ranked reply order
can be read as chronological. The alternative — re-sorting replies by time — would contradict the
no-reorder rule, and a permanent "ranked by x.com" line would be chrome on every thread frame.

### Tombstones, limited and withheld in a thread

Phase 2's rules stand; this phase states how they occupy their place in a conversation.

| Visibility | Rows | Place in the conversation |
|------------|------|---------------------------|
| `Visible` | normal block | — |
| `Limited` | its text **and** the `limited` marker on the head row | unchanged from Phase 2; a limited reply is a reply like any other |
| `Unavailable` | **`post unavailable` as the block's only body row**, at the block's indent, and no head row when the content value carries no author and no stamp (which is what `domain` models). If a tombstone does carry an author and a stamp, the head row renders as usual — the renderer keys on what the content value holds, not on a rule about tombstones. `[INFERENCE]` that some tombstones carry an author/date; Phase 2's own 80-column frame draws one that way. | the block keeps its place and its indent: the reply is still visibly the third reply even though it says nothing |
| `Withheld` | `post withheld` as the block's only body row, same shape as the tombstone | same; `[INFERENCE]` no recorded response carries one — the row exists because a state without a literal would render as a blank row, and Phase 2's totality rule for failures applies to visibility too |

A tombstone is selectable and `enter` opens its conversation: a deleted post can still have replies
worth reading. Nothing about a tombstone is an error, and no failure state is raised by one.

### "partial thread" — the conditions, and the non-conditions

`THRD-03`. The label is conditional. It is printed only when the frame can name *why* the thread is
incomplete, and never as a standing disclaimer:

| # | Condition, as the content value can see it | Statement printed |
|---|--------------------------------------------|-------------------|
| 1 | the reply walk holds a cursor the upstream would not advance (the cursor repeated, or a page contributed no unseen reply — Phase 2's stall detection, reused verbatim) | `partial thread - the reply walk stopped here`, at the reply step, after the last reply |
| 2 | the focal post answers a post the frame does not hold (`Focal.ReplyTo` names an id that is in neither the ancestors nor the focal post) | `partial thread - the post above is not reachable`, directly above the focal block, preceded by one blank row |
| 3 | the answer carried no replies, no reply cursor, **and** the focal post's own reply count is greater than zero | `partial thread - replies are not reachable`, at the reply step. `[INFERENCE]` the decoder must retain `Counts.Replies` for this: the number is never printed (`REND-01`), it is only the evidence for the statement. Verify against the recorded `TweetDetail` fixture before implementing; if the field is absent, drop this row rather than guessing |

**Not conditions, deliberately:**

- **end of the reply list** (`Next` empty, no stall): nothing is printed. The upstream says there is
  nothing more; the frame repeats that by saying nothing, exactly as Phase 2's timeline does.
- **a failed page**: the posts received stay, the failure goes to the status line
  (`FEED-05` inherited), and no `partial thread` line is printed. One fact is stated once.
- **a limited or withheld post inside the thread**: those are per-post states with their own words
  (above), not a statement about the thread.

### Pagination: the reply walk, without a key of its own

- **No "load more replies" control exists.** No line, no link, no key. Phase 2's implicit trigger is
  inherited exactly: reaching the last loaded row of the **reply stream** with `j`, `ctrl+d`,
  `pgdown` or `G` requests the next page of the reply walk (single-flight; further presses are
  no-ops, not a queue), the selection does not move until the page arrives, and the anchor holds so
  a late page never moves what the user is reading. Reaching an ancestor row is **not** a trigger:
  the ancestors arrived with page one and are not a walk (`04-CONTEXT.md`).
- The **only** on-screen evidence that more replies exist is the `+` in the position field
  (`2/6+`), exactly as in Phase 2. *Named compromise, inherited:* a reader who never walks to the
  last reply never sees that there is more. A `more replies` line in the pane was rejected: it would
  be chrome in every frame, and the list has no selectable non-post rows by design.
- A stalled walk ends the walk, prints condition 1 above, and never retries the same cursor. The
  `notice` field does **not** repeat it (the pane says it once).
- `r` in a thread re-reads the thread: the answer's posts replace the frame's posts (post ids
  already held keep their read state), the walk's cursor becomes the answer's, the selection is
  held by target id and falls back to the same id's shallowest occurrence, then to the focal post,
  and the anchor holds the selected block's head row. The `notice` field announces
  `{n} new replies` (reply ids the frame did not hold before) or `no new replies`.
  *Deviation from Phase 2's "prepend only unseen":* the reply section is a ranking the client
  cannot merge into, so re-reading it is the only honest way to make it current. The same key keeps
  the same meaning ("make this list current"), and the selection/scroll promise is kept by target
  id rather than by position.

### What is deliberately absent from a conversation

Inherited from Phase 2 and confirmed unchanged: no avatars, no display names, no `@` sigils, no
engagement counts (`REND-01` — see below), no icons or emoji decorations, no rules, boxes,
alternating backgrounds, no inline images, no printed URLs, no reply marker beyond the words above,
no numbering of posts, no relative times, no heading row, no "load more" affordance, no sticky
"thread context" bar.

- **`REND-01` and counts.** Phase 2's `### The post block` parenthetical ("the detail view is where
  `Counts` may be printed as plain text") is **superseded**: `REND-01`'s own words are "list and
  detail screens … no engagement counts", and this phase's detail view is the thread frame.
  `Grammar.ShowCounts` stays `false` in every grammar this phase ships, and no thread frame
  contains a number from `Counts` — including the focal post's reply count, which condition 3 above
  *consults* as evidence and never prints.
  **The trade-off, recorded rather than hidden** (`04-CONTEXT.md` flags the two documents as
  disagreeing and asks the user to settle it): the consequence of this choice is that a reader of a
  thread cannot see how many replies, reposts or likes a post has without leaving for the browser.
  The alternative — one plain-text counts line on the focal post only, behind one
  `Grammar.ShowCounts` flag and one marker literal, with the list staying count-free either way —
  costs one flag plus one golden-frame regeneration if it is ever wanted. This spec takes the
  requirement's own words; it does not take the Out-of-Scope table's aside.
- **Display names.** Printed by no grammar this phase ships; Phase 5's profile header is their
  single home (see the deviation note above).
- **No per-reply metadata row.** No reply-count line, no "3 replies" separator, no `sortIndex`, no
  engagement word anywhere.

## The Status Line

Phase 2's row, order, separator rule and drop order stand. **This phase adds no field and changes
no drop order** — stated explicitly:

```
{state}  {remedy}  {notice}  {list}  {position}  {budget}
```

Drop order when the line does not fit `W`: `notice`, then `position`, then `list`; `state`,
`remedy` and `budget` are never dropped. One left-aligned run.

What this phase changes is **vocabulary only**:

| Field | Value in a thread frame |
|-------|-------------------------|
| `list` | `thread` |
| `position` | `{block index}/{blocks}` plus `+` while the reply walk holds a cursor, e.g. `2/6+`. The count is the posts the frame holds — ancestors, the focal post, its continuations and the replies read so far; the index is the block the selection is inside (a quoted post does not move the number) |
| `notice` | `loading replies` while a reply page is in flight; `{n} new reply` / `{n} new replies` / `no new replies` after `r`; empty otherwise (the partial-thread conditions are stated in the pane, not here) |
| `state`, `remedy` | Phase 2's state table, unchanged and unextended: every failure class of the classifier already has a row, and a thread failure is one of them |
| `budget` | unchanged, including in every thread frame and every failure frame (`OPS-02`) |

## Width Model

Phase 2's model stands in full: one measurement in `internal/text` (`Width`, `Wrap`, `Pad`,
`Truncate`), the `$TMUX` dispatch, no second measurement anywhere, `A4`–`A7`, the frame being a pure
function of `(state, W, H)`.

Additions and confirmations for this phase:

- The body measure is Phase 3's formula with the reply term added:
  `min(W - 1 - BodyIndent - 2*min(quoteLevel, QuoteDepthCap) - len(BodyPrefix) - ReplyIndent*replyLevel, MeasureCap)`
  with `replyLevel ∈ {0,1}` — see `### Indentation, depth and the measure`.
- `A4` applies to the thread's frames too: for every fixture post and every `w` in
  `{1, 2, 3, 5, 8, 55, 77, 96}` the wrap/pad/truncate properties hold **at both reply levels and
  at both quote levels**, and the deepest legal row (reply + quote + quote) never exceeds `W`.
- Marker rows are subject to the same cap as Phase 2's head rows: a marker chain that would push
  the row past `W` is truncated with `~` in its last cell, and the test suite asserts that no
  stored frame needs that (the markers this phase adds are short and the identity column is
  fixed-width).

## Keymap Contract

Phase 2's table, help overlay and `keys` subcommand stand. **This phase adds one row and one field
on the row value, and changes no other row's behaviour.**

| Keys | Action | Help text (rendered verbatim) | Group | Screens |
|------|--------|-------------------------------|-------|---------|
| `enter` | `open` | `open the selected post or account` | navigate | all |

- **`open` is one action for both row kinds** (a post, or — from Phase 5 — a user row). One key
  cannot carry two actions in one table: the matcher is a linear scan, so two rows sharing `enter`
  would be ambiguous. The help text names both targets.
- `enter` on a quoted post opens the quote's own conversation (`THRD-02`); on a tombstone it opens
  the tombstone's conversation; on an unchanged row it does exactly what the help says.
- **Pagination has no key** — inherited, and the reply walk is the same trigger
  (`### Pagination: the reply walk, without a key of its own`).
- **No key exists for the partial-thread conditions**: they are statements, not actions.

**The `screens` field (new, and the reason).** The row value gains a `screens` field beside Phase 3's
`HelpCovered`, naming the frame kinds a row applies to: `all`, or a list drawn from
`{home, search, thread, profile}` (later phases add their own kinds to that list). Reason: `t`
(Phase 2's `toggle-feed`) has no meaning in a thread frame, and Phase 2's rule is that no key is
documented that does not work. With the field, the `?` overlay lists the rows applicable to the top
frame and pressing an inapplicable key does nothing, silently and correctly; an *applicable* key
whose action has nothing to act on reports one honest line instead (`04-CONTEXT.md`'s rule, and the
mechanism Phase 5's `s` uses when there is no order to switch).

| Keys | Action | Help text | Group | Screens |
|------|--------|-----------|-------|---------|
| `t` | `switch-list` | `switch what this list shows` | feed | `home` |

- **Coordination note, stated rather than hidden.** `04-CONTEXT.md` records this row's final form as
  action `switch-list`, help `switch what this list shows`, screens `home search`; `05-CONTEXT.md`
  then assigns the search frame's order toggle to its own key (`s`, Phase 5). With `s` owning the
  search order, this row's screens are **`home`** — anything else would list a key in a search frame
  that does nothing there, which is exactly what the field exists to prevent. The action and help
  words are kept as `04-CONTEXT.md` wrote them; only the screens value narrows, and Phase 5's spec
  states the same resolution from its side.
- This row is still a **modification of a Phase 2 row**, not an addition: action `toggle-feed` →
  `switch-list`, help text `switch between following and for you` → `switch what this list shows`.
  Phase 4 writes it, so that the two parallel phases never edit the same row twice.
- **The `enter` row carries Phase 3's two help texts** (`Help` and `HelpCovered`), as every row
  must, since the `?` overlay works under a cover.
- **Key collisions with Phase 3 are resolved in Phase 3's favour** (`04-CONTEXT.md`): Phase 3 lands
  first and its state keys work in every state. Phase 3's landed allocation is `m`, `c`, `1`–`4`
  and `ctrl+p`, which does not collide with `enter`; **if a collision appears against the keymap as
  it actually landed, this phase's row moves.** In `panic` the whole table is shadowed
  (Phase 3's T10), so `enter` is swallowed there like everything else.
- The `keys` subcommand's output is **unchanged**: `keys<TAB>action<TAB>help`, three fields, in
  table order. The `screens` field is not printed there — a listing subcommand has no frame
  context, so printing applicability would be a claim about nothing. REND-05 is unaffected: help,
  matcher and completion still derive from the one table.
- **Cost of the field, stated:** one field on the row value, one filter in the overlay's row
  selection, one test asserting that a key whose screens exclude the current frame is not listed
  and is not dispatched. No new package, no new table.
- **Help overlay rule (Phase 2 refined):** the overlay replaces the pane with the rows applicable to
  the top frame, in table order, keys column 16 cells, no heading, no border; `?` and `back` close
  it and every other action is ignored.
- The row list in Phase 2's table is otherwise unchanged: `j`/`k`, `ctrl+d`/`ctrl+u`,
  `pgdown`/`pgup`, `g`/`home`, `G`/`end`, `r`, `t`, `?`, `q`/`esc`, `ctrl+c`. `r` and `q`/`esc` work
  in a thread with the meanings given above and in Phase 2. `o` and `y` stay unbound: Phase 7 owns
  media and link actions.
- The back stack, its frame contents and its four restore observables are Phase 2's, unchanged. A
  thread frame's contents are `{focal post id, the posts in frame order, the reply-walk cursor, the
  walk's stall flag, the partial-condition flags, the selected target, the anchor}`. Non-top frames
  are frozen; `q`/`esc` restores the previous frame byte-identically with zero new requests.

## Content / Presentation Split

Phase 2's split stands: content owns what is true about a post; presentation owns every character
the user sees; no `domain` value holds a rendered string; no renderer ever reads upstream JSON.

### Content this phase adds (`internal/domain`, produced by `internal/xsource`)

| Field | Notes |
|-------|-------|
| `Thread.Focal Post` | the post the frame was opened on |
| `Thread.Ancestors []Post` | root → parent, the answer's own order; may be empty; may hold tombstones |
| `Thread.Groups []Group` with `Group{Kind, Posts, More Cursor}` and `Kind ∈ {SelfThread, Replies}` | the self-thread group renders at indent 0 with `continued`; the reply group at one step. `Related`-rail entries (`tweetdetailrelatedtweets…`) are classified and dropped by the decoder, never rendered (`[INFERENCE]` from the research's instruction walk; the planner validates it against the fixture) |
| `Thread.Next Cursor` | the per-module reply cursor (`ShowMoreThreads`) passed back as the top-level cursor of the next request |
| `Thread.Requested`, `FetchedAt` | as Phase 2's `PostPage` |
| `Post.Counts.Replies` | retained (Phase 2 already parses it); **never printed**, consulted only by partial-thread condition 3 |
| visibility | Phase 2's four states, unchanged; the thread frame is where all four are reached in practice |

The `Source` port grows one method, in the same shape as `Home`, and the value it returns has the
shape of Phase 2's `PostPage`:

```go
// internal/domain
// Thread returns the conversation containing a post: the chain above it, the post
// itself, and one page of its replies. An empty cursor asks for the first page; the
// answer's Next asks for the page after it.
Thread(ctx context.Context, id PostID, c Cursor) (ThreadPage, error)

type ThreadPage struct {
    Focal     Post      // the post the frame was opened on
    Ancestors []Post    // root → parent, the answer's own order; may be empty
    Groups    []Group   // in the answer's order
    Next      Cursor    // the reply walk's cursor; empty at the end of the walk
    Requested int       // as Phase 2's PostPage.Requested
    FetchedAt time.Time
}

type Group struct {
    Kind  GroupKind  // SelfThread renders at indent 0 with `continued`; Replies at one step
    Posts []Post
    More  Cursor     // this group's own "show more" handle; empty when the group is complete
}
```

Nothing about the wire crosses the port: no module kind, no instruction name, no cursor type, no
`sortIndex`.

### Presentation this phase adds (`internal/render`)

Phase 2's `Grammar` gains exactly this much, and no more:

| Field | Value in `Plain` | What it decides |
|-------|------------------|-----------------|
| `ReplyIndent int` | `2` | cells added to every row of a reply block; one reply level only |
| `Markers.Focal string` | `focal` | the focal post's marker, placed by Phase 3's `MarkerPlace` like every other marker |
| `Markers.ReplyTo string` | `reply to {handle}` | the reply-elsewhere marker; `{handle}` is Phase 3's placeholder, expanding to `CoverAlias.Handle`, so a cover leaks no real handle and may use `{ref}` instead |
| `Markers.NoReplies string` | `no replies` | the empty reply section's statement |
| `Markers.LoadingThread string` | `loading thread...` | the first-page statement |
| `Markers.PartialStopped string` | `partial thread - the reply walk stopped here` | condition 1 |
| `Markers.PartialAbove string` | `partial thread - the post above is not reachable` | condition 2 |
| `Markers.PartialHidden string` | `partial thread - replies are not reachable` | condition 3 |
| `Markers.Withheld string` | `post withheld` | the fourth visibility state: Phase 2's `MarkerSet` names `Limited`, `Unavailable` and `MissingText` but carries no literal for `Withheld`, so this row is added rather than inherited |

Everything else about the thread — the block order, the reply step's *use*, the selection, the
position arithmetic, the walk — is **not** grammar and is identical under every grammar. A test
asserts every shipped grammar's marker set is complete (no empty string), following Phase 2's
totality test for the state tables.

### Through the cover (DSGT-08)

Every surface in this phase is expressible through the Phase 3 `Grammar`/cover seam, and nothing
needs a second renderer:

| Thread element | Carried by | A cover supplies |
|----------------|-----------|------------------|
| the focal post's identity | `Grammar.Identity` (already the alias seam) | nothing new |
| `reply to {handle}` | `Markers.ReplyTo` with `{handle}` through `Identity` | its own template (e.g. `rel=reply_to:<alias>`) |
| the reply step | `ReplyIndent`, or a cover's own record prefix | one number, or its own `rel=` field |
| ancestors / replies / continuations | the block order, which is not grammar | nothing |
| the partial-thread statements | `Markers.Partial*` | its own statements (a log cover would render them as `WARN …partial=true`) |
| the empty / loading statements | `Markers.NoReplies`, `Markers.LoadingThread` | its own lines |
| counts | never printed in any grammar (`ShowCounts` false everywhere) | nothing: `DSGT-09` is satisfied by construction |
| selection, position, walk, status line | frame composition and the shell | nothing |

The one thing a cover must **not** do is state the reply order, the reply step or a relationship in
a way that contradicts the content; the seam above gives it no place to.

**The cost of the seam, named.** This phase adds nine literals (the table above), and each needs
**two spellings**: the plain one in `internal/render/copy.go` and one in the covered copy set Phase 3
established for its covers, because the `?` overlay, the status line, the failure sentences and the
pane statements all render under a cover too. A covered frame that fell back to a plain literal
would speak in the product's voice, which is what `DSGT-09` forbids. That is the whole cost: nine
template rows, one of them a marker and eight of them statements, with the covered wordings worded
by Phase 3.
