<objective>
`x-terminal update` replaces the installed binary with the asset this platform's GitHub Release
carries, after verifying the digest the same Release publishes, and the next launch reports the new
version. One flag asks the question without installing (`--check`), one flag asks for the same or an
older release on purpose (`--force`), and every way it can fail is a named state that names its
`RUNBOOK.md` section.

Purpose: this build is now published from a **public** repository, and the install path the README
documents is a manual download, a manual `sha256sum -c` and a manual `install`. All three are
mechanical and all three are easy to get subtly wrong — the wrong asset for the platform, the digest
file taken from a different tag, a `0644` copy, a partial file left in `~/.local/bin`. The verb is that
procedure with the parts that can lie removed: the asset list comes from the Release itself rather than
from a tag-derived name, the digest is the per-asset file that names its own artifact, the payload must
carry the tag it was published under, and the replacement is a temp file in the target's own directory
renamed over it, so the target path is never a partial binary.

Output: the GitHub release wire and the atomic installer in `internal/release`, the verb's body and its
state vocabulary in `internal/cli/update.go`, one row in `internal/cli/cli.go`'s table, the amended
`transport` builder allowlist, the amended `persistence` destination table and its derived promise, the
new `RUNBOOK.md` section with its coverage rows, and the live old → new proof against the real Release.

The five decisions this plan is required to state, each implemented and argued in the task named:

(a) **Where the downloader lives.** `internal/release` (Tasks 1 and 2), a new package root, and the
    audit's `transport` allowlist gains it (`requestBuilderOK`, `internal/audit/readonly.go`). The
    alternative — building these GETs inside `internal/xweb` — is the dishonest one: `xweb` is the
    x.com socket (session-bound, limiter-bound, and its `NoRedirect` rule is a statement about x.com),
    a GitHub release is none of those, and a request that carries no x.com credential has no business
    in the package that owns the credential. The existing comment above `requestBuilderOK` already
    names each root with its justification; this is that pattern applied once more, and both GETs it
    builds stay inside the check's method arm, so nothing is exempted and no method constant other
    than the one `MethodGet` spelling is added anywhere.

(b) **Which digest is authoritative.** The per-asset `.sha256` beside the asset (Task 2), not
    `SHA256SUMS`. The release workflow writes the per-asset file as `sha256sum "${name}" > "${name}.sha256"`
    and builds `SHA256SUMS` as `cat ./*.sha256 | sort -k2`, so the two agree line for line — but the
    per-asset file names the artifact in its own line, which means verification has no row-selection
    step that could pick a different platform's digest, and `ParseDigest` can assert the name it read
    against the name it asked for. What this proves is stated where it is used: the digest and the
    payload come from the same origin, so it defeats corruption, truncation and a mismatched asset, and
    it is not a provenance or authenticity proof.

(c) **The symlink stance.** The updater resolves the path and replaces the **resolved target**,
    printing which path it wrote (Task 2), and it does not inherit `internal/session`'s refusal. The
    two are not the same case: `session.Load` refuses a symlink because the file that was mode-checked
    is then not the file that is read, which is a security property of a credential. A symlinked binary
    — a `~/.local/bin` entry pointing into a versioned directory, which is an ordinary Go-install shape
    — has no such property: the file being replaced is identified by its resolved path and the payload
    is identified by its digest. So `os.Executable()` is followed by `filepath.EvalSymlinks`, and the
    printed line says which real path took the new bytes.

(d) **A check-only mode exists, and it is called `--check`,** not `--dry-run` (Task 1). The question
    "is there a newer release?" is a read of the upstream, and `--check` is the word this codebase
    already uses for asking without doing (`doctor --probe`). A `--dry-run` would promise a rehearsal
    of a mutation this verb does not offer in pieces. Exit codes follow the verb's own single rule,
    stated in the task: an answer the verb can print — up to date, an upgrade available, a downgrade
    refused, a build with no release identity — is `ExitOK`, and `ExitError` is reserved for the states
    where the verb could not do the thing it was asked (the release unreachable, no asset for this
    platform, the download unverified, the install path unwritable). A mistaken invocation is
    `ExitUsage`, as everywhere.

(e) **What `os.Executable()` means here.** It is the file this process was started from, not the file
    the operator believes is installed, and it is the only path the verb may touch (Task 2). On Linux
    it reads `/proc/self/exe`, which is already resolved; on macOS it can carry a symlink, which is why
    `filepath.EvalSymlinks` runs unconditionally rather than being left to the platform. The process
    already running keeps the image it was started with — a `rename` over a running executable is
    allowed and the running process is unaffected — so the new binary takes effect at the next launch,
    and the verb prints that in as many words instead of letting the operator believe the change is
    live.

Two promises are deliberately **not** amended by this plan, and each for a reason the tasks state:
`account` ("exactly one session path and one credential pair") stays literally true because no GitHub
token is required, none is written anywhere, and none reaches a config key — the token is read from the
environment and carried as a `session.Secret`, so it is redacted by construction rather than by care;
and the `distribution` check's comment and promise line, `PROJECT.md`'s Out of Scope entry and
`README.md`'s "What this is not" are the landed work of the concurrent quick task `261016` that recorded
the public repository, so those three files are read-only inputs here. `README.md` is therefore outside
this plan's `files_modified`: the update verb's user-facing documentation is its usage line and its
`RUNBOOK.md` section, and README's owner of record in this window is that other task.

This is a post-milestone feature, not a roadmap requirement. It touches no x.com request: `internal/xweb`,
`internal/xsource`, `internal/domain`, `internal/screen`, `internal/render`, `internal/tui` and the six
read operations' shapes are untouched, and the new package's requests carry no session cookie and spend
no account budget.

**`internal/release/release.go`: the GitHub release wire, and why it is not `internal/xweb`.** A new
package, one file, whose package comment says what it is for and what it refuses to be: the release wire
for the update verb, GET-only, holding no x.com session and borrowing no x.com limiter. It builds its
client from `xweb.NewTransport(cfg)` — the one `http.Transport` every request in this program goes
through, so the operator's resolved proxy and `NO_PROXY` rules apply here exactly as they do to a read —
and wraps it in its own `*http.Client` with a named `Timeout` and net/http's **default** redirect policy.
The default is deliberate and the comment says why: an asset URL answers 302 to a signed object URL, the
`NoRedirect` rule `internal/xweb` ships with is a statement about x.com (a redirect there means the
request was refused), and net/http drops `Authorization` on a cross-host hop, which is what the signed
URL requires. Nothing in this package waits: no retry, no backoff, no `time.Sleep`.

- `type Release struct { Tag string; Assets []Asset }` and `type Asset struct { Name string; Size int64; URL string }`.
- `type Client struct { http *http.Client; token session.Secret; apiBase, downloadBase, repo string }`, with
  `func New(cfg config.Config, token session.Secret) (*Client, error)` setting the two bases and the
  repository (`apiBase` `https://api.github.com`, `downloadBase` `https://github.com`) and returning an
  error only when the transport cannot be built. The fields stay unexported so that a test inside the
  package points them at an `httptest` server without the production type growing a way to be lied to.
  The token is a `session.Secret`, never a `string`: that type redacts every formatting path
  (`String`, `GoString`, `Format`, `MarshalJSON`, `MarshalText`, `LogValue`), which is the same
  mechanism that keeps the cookie out of a bug report, and it is the reason the plan claims the token
  cannot be printed rather than promising that nobody prints it. It has exactly one reader, `Reveal`, and
  one caller, the header builder.
- `func (c *Client) Latest(ctx context.Context) (Release, error)` issues exactly one
  `http.NewRequestWithContext` GET to `apiBase` + `/repos/` + repo + `/releases/latest`, sets the headers
  in one place (`Accept: application/vnd.github+json`; `User-Agent: x-terminal/<version or "working tree">`
  — the API answers 403 without one, so the header is a requirement and not a courtesy; and
  `Authorization: Bearer <token>` only when the token is non-empty, which is the whole of the
  visibility-agnostic design: a public repository needs no token, a private fork or a future flip still
  works, and nothing verifies a permission the request did not need), sends it through `c.http.Do`, and
