<objective>
One key translates the post the cursor is on, through x.com's own translation service, and moving the
cursor off that post reverts it to the original. The translated view is a property of the selection
rather than a state of the list, so the reader never leaves the screen and no pane, feed or list is
rewritten to hold a translation.

Purpose: the mechanism that makes this cheap is one REST GET on `api.x.com` that is not GraphQL and
not in the operation registry, so the feature costs zero bytes of change to the requests this build
already makes. The whole point of choosing it over asking the feed for inline translations is that
`HomeLatestTimeline`, `HomeTimeline`, `TweetDetail`, `SearchTimeline`, `Bookmarks` and `Likes` keep
their exact request shape — not one variable, one header, one feature switch or one method changes.
That is the constraint the plan is built around, and Task 1's proof of it is that `internal/xsource`'s
four read adapters are never opened.

Output: the measured endpoint and its request builder in `internal/xweb`, the bytes-to-domain parser
in `internal/xsource`, the port in `internal/domain`, the selection-scoped translated view and its
memory-only one-press-per-post cache in `internal/tui`, one keymap row, two status-line notices, the
`translate.language` config key and the doctor's presence fact for it, the amended repair section in
`RUNBOOK.md`, and the dated measurement record.

The five decisions this plan is required to state, each implemented and argued in the task named:

(a) Which file owns the new REST request, and why the audit's transport check stays satisfied —
    `internal/xweb/translate.go` (Task 1). The check's builder allowlist is `internal/xweb`,
    `internal/netcheck`, `internal/opsgen` and its method arm passes anything that is neither GET nor
    a POST outside `internal/xweb/graphql.go`; this request is a GET built inside `internal/xweb`, so
    both arms pass with no exemption added, no allowlist widened and no new `http.Method*` spelling
    anywhere. `readonly`/`opnames` stay satisfied because the new file spells no registry operation
    name and no name in the audit's write table (verified: the endpoint path and the response's keys
    appear in neither table, and the name pattern the check collects is
    `^[A-Za-z][A-Za-z0-9_]*$` — `Some`, `Missing`, `translation` and `translateTweet` are in neither
    set). `persistence` stays at its six printed destinations because nothing about a translation is
    written anywhere, and `timers` stays satisfied because the product adds no wait (the 4-second
    spacing is a property of the measurement, not of the shipped path).

(b) Where the translated-vs-original choice lives and how moving reverts it — `internal/tui/model.go`'s
    `Model.translations` (Task 2). The choice is not stored as a flag: a post renders translated
    exactly when it is the row the selection names AND its id is in that memory-only map, and the swap
    happens in `blocksIn`, the one place the pane's rows are built. A selection move therefore reverts
    the previous post by construction — there is no second fact to keep in step — and re-selecting a
    post whose id is in the map spends nothing, because the map is looked up before any request is
    built.

(c) Which key, and what `?` and `x-terminal keys` show — `T` (shift-t) (Task 2). Lower-case `t` is
    already "switch what this list shows", and the shared context's remaining bindings leave no other
    free spelling that says what the key does. A shifted letter is a distinct binding under the shell's
    two-ask matcher (`keyAction` asks `Keystroke()` then `String()`), which the shipped `G` row already
    proves. The row it needs a covered wording, and gets one, because the plain wording names a post.

(d) Whether the action belongs in `coverBreaking` — it does not (Task 2), and the plan says why in
    that task: the predicate's own documented rationale is handing a string that identifies the real
    upstream to a program outside this process or to the clipboard, and a translation is an
    in-process request to x.com itself, about a post that account has already fetched, handing nothing
    to any other program. The covered pane already carries post bodies in its own grammar, so gating
    it would refuse an action that reveals nothing the cover does not already show.

(e) How `Missing` and a non-200 each render — Task 2 for the first, Task 1 and Task 2 for the second,
    both on existing states, with `RUNBOOK.md#request-shape-drift` amended in Task 3. A `200` whose
    `translationState` is not `Success` (or whose translation is empty, or whose `id_str` is not the
    post asked for) is a successful read that carries no translation: it renders as the new
    `render.NoticeNoTranslation` in the notice field and puts no body in the pane. A refusal is
    classified by the existing `xweb.Classify` and returned as the existing `*xweb.APIError`, so it
    reaches the state field as the classifier's own word through the existing `deps.Failure` mapper —
    `bad request` / empty-bodied `404` → `#request-shape-drift`, `429` → `#429`, `unclassified` →
    `#unclassified` — with no new `domain.FailureKind`, no new doctor anchor and no new RUNBOOK
    section. The one RUNBOOK edit is to the repair sentence of `#request-shape-drift`, which today
    tells the reader to fix the variables or refresh the ids and is not the repair for an endpoint
    that is not in the registry and cannot be in it.

This is a post-milestone feature, not a roadmap requirement, and it is scoped to the read/transport
seam: no signature in `internal/domain`'s content model moves, `render.Blocks` keeps its signature,
and the list walk, the screens and the request shapes of the six existing operations are untouched.
</objective>

# The endpoint, measured on this host on 2026-10-16 through the operator's own session cookie and the
# proxy at http://127.0.0.1:7897. Every request in that measurement went through internal/xweb's own
# client (`Client.Do`, so through the limiter), not curl: curl with hand-assembled headers produced
# spurious `401 {"code":89}` on requests this client answered `200`, so a curl result that disagrees
# with the product's own client is the curl's problem and never the upstream's.
#
#   GET https://api.x.com/1.1/strato/column/None/tweetId=<ID>,destinationLanguage=Some(<LANG>),translationSource=Some(X),feature=None,timeout=None,onlyCached=None/translation/service/translateTweet
#
# There is no `.json` suffix, and that is the single most expensive thing to get wrong: with the suffix
# the answer is `HTTP 404 {"code":34,"message":"Sorry, that page does not exist"}`, a false negative
# that is indistinguishable from "this endpoint does not exist". The bundle's own call is
# `apiClient.get(path, {}, headers, "")`, and `get(e,t,r,i=".json",n)` builds `/1.1/${path}${i}` — the
# empty fourth argument is what removes the suffix.
#
#   request          | answer
#   -----------------+--------------------------------------------------------------------------
#   zh-CN            | 200, 1,167 bytes for id 2110709021544153425, `translationState:"Success"`
#   de               | 200, the same post in German
#   ja               | 200, the same post in Japanese
#   en (en post)     | 200, `"X is for everyone"`, `"Success"`
#   id=1             | 200, `"translation":""`, `"translationState":"Missing"`
#   the same path    | 404 `{"code":34,...}` — the suffix appended
#   with `.json`     |
#
# So a `200` does not mean a translation exists, and a pane must never present an empty body as one.
# The response shape read by this plan is `{"id","id_str","translation","translationState",
# "sourceLanguage","localizedSourceLanguage","translationSource","destinationLanguage","entities"}`;
# of those this build reads `id_str`, `translation` and `translationState` and nothing else.
#
# The header set is the one `graphQLRequest` already sends, verbatim: `authorization: Bearer
# <WebBearer>`, the `auth_token`+`ct0` cookie pair, `x-csrf-token: <ct0>`, `x-twitter-auth-type:
# OAuth2Session`, `x-twitter-active-user: yes`, `x-twitter-client-language`, a browser `user-agent` and
# `content-type: application/json`. No `x-client-transaction-id` is needed, and that is mechanical
# rather than lucky: the bundle's own host allowlist for that signer is

**Where the request is built, and why it is built there.** The new REST request lives in
`internal/xweb/translate.go`, beside `graphql.go`, because that package is the wire and it is already
one of the three roots the audit's transport check allows to call `http.NewRequest*`. Two consequences
have to hold and are asserted in this task's verify: the method is `http.MethodGet` (the check's method
arm reports POST outside `internal/xweb/graphql.go` and any other method anywhere, and `MethodGet` is
the one `http.Method*` spelling its constant arm exempts), and the file adds no exemption, widens no
allowlist and changes no check. The translation service is **not** a GraphQL operation, so nothing is
added to `internal/xweb/volatile/registry.json`, to `opClass` in `internal/audit/readonly.go`, or to
`postOperations` in `graphql.go` — a registry entry for it would be a claim that a bundle carries a
query id for it, which is false, and `checkOpNames` would then be auditing a promise about a request
this build cannot make.

**`internal/xweb/translate.go`.** One method, exactly one request, no retry:

- `func (c *Client) Translate(ctx context.Context, id, lang string) ([]byte, error)`. Its doc comment
  states the measurement, with the date, the exact URL shape, the "no suffix" rule and the statuses
  (the shared context block carries them: `200`/1,167 bytes for a live post to `zh-CN`, to `de` and to `ja`;
  `200` with `translation:""` and `translationState:"Missing"` for a nonexistent id; `404` with
  `{"code":34}` for the suffixed form), the header set and its source, and that the bundle's own call
  site passes the empty fourth argument that removes the suffix. It cites the file in the bundle
  (`apiClient.get(path, {}, headers, "")` → `get(e,t,r,i=".json",n)` → `/1.1/${path}${i}`) so the next
  reader can re-derive the rule instead of trusting it.
- The URL is assembled by one small function that takes the id and the language and returns either the
  string or an error, and it validates both before assembling: the id against `^[0-9]{1,20}$` and the
  language against a conservative tag pattern (two or three letters, then zero or more
  `-`-separated alphanumeric subtags: `zh-CN`, `de`, `ja`, `en` all match; anything holding a
  parenthesis, a comma, a slash, a space or a percent sign does not). A refused value returns an error
  and no request is built, because a value interpolated into a path by hand is exactly the hazard
  `graphql.go`'s `query()` comment describes for a query parameter, and there is no `url.Values` for a
  path. Do **not** run the column expression through `url.PathEscape`: it escapes the parentheses and
  the result is a different request (`Some%28zh-CN%29`), which was never measured.
- The path is the measured one, in the measured order, with the segments that are not the post id or
  the language as literals: `APIBaseURL` + `/1.1/strato/column/None/tweetId=` + id +
  `,destinationLanguage=Some(` + lang + `),translationSource=Some(X),feature=None,timeout=None,onlyCached=None`
  + `/translation/service/translateTweet`. The comment says which part of that is the upstream's own
  vocabulary (`strato`, `column/None`, `translationSource=Some(X)`, `feature`/`timeout`/`onlyCached`)
  and that none of it was chosen here.
- The session check is `GraphQL`'s own: a client without a valid session returns
  `session.ErrNoSession` wrapped and sends nothing, because an unauthenticated request to this endpoint
  is a `403` with an empty body, i.e. a spent request that measures nothing.
- The request goes out through `c.Do` — the limiter every other request passes through — and its answer
  is read with the same bound as `GraphQL` (`maxResponseBody`, read with the same `+1` guard, so an
  over-long answer is a named error rather than a truncation). Its answer is classified by the same
  `Classify`, and a non-success becomes the same `*APIError` with the same bounded `apiMessage` detail
  and the same reset instant. Nothing new about failure is invented here; the whole point is that a
  refusal from this endpoint reaches the screen as the classifier's own word.
- The body is returned as bytes only when the outcome succeeded; the decoding is the next package's job.

**`internal/domain/translate.go`.** The port, declared by its consumer the way `domain.Threads` is:
`type Translation struct { Text string; Available bool }` and
`type Translator interface { Translate(ctx context.Context, id PostID, lang string) (Translation, error) }`.
`Available` is the whole of what this package may say about the answer's state: `false` means the
service answered and carries no translation for this post — never "the request failed", which crosses
the seam as an error. The doc comment says so, and says that no upstream word (`Success`, `Missing`,
`translationState`) appears in this package, which is the `.planning`-era rule this file has to keep:
the words a user reads are `internal/render`'s and the states the status line names are the
classifier's. The language is a parameter of the port rather than a field of the adapter because it is a
setting, and a setting resolved once belongs at the composition root (Task 3), not in a value that is
copied per read.

**`internal/xsource/translate.go`.** The adapter that turns the answer's bytes into a domain value,
which is this package's stated job ("everything about the answer's shape is resolved by the parsers"):

- `type Translator interface { Translate(ctx context.Context, id, lang string) ([]byte, error) }` — a
  second, small interface rather than a widening of `GraphQLer`, because `GraphQLer`'s own doc comment
  says it is the one *GraphQL operation* call this adapter makes and this is not a GraphQL operation.
- `func (a *Adapter) WithTranslator(t Translator) *Adapter` returns a copy carrying it, the way
  `WithViewerID` does, and says why in the same words: a composition root can build the adapter and the
  client once and hand both the same session. A nil translator — a build with no translation endpoint —
  makes `Translate` return a typed `ErrNoTranslator` rather than panicking, beside
  `withholds`/the other package errors.
- `func (a *Adapter) Translate(ctx context.Context, id domain.PostID, lang string) (domain.Translation, error)`
  issues exactly one call and hands the bytes to the parser. Nothing here retries: a refusal is a second
  diagnosis, not a second attempt, which is the discipline `RUNBOOK.md`'s first section states.
- `func ParseTranslation(raw []byte, id domain.PostID) (domain.Translation, error)` is pure over the
  bytes and is the whole of the honesty rule, in three arms: a body that is not JSON, or that carries
  no `id_str`, is a typed error naming the JSON path — the `detail.go` idiom, because a body this build
  cannot read must never render as a post with no translation; a body whose `id_str` is not the post
  that was asked for is a typed error too, in `detail.go`'s own words ("an answer about a different post
  is an answer to a different question"); and a body that is about the right post with
  `translationState == "Success"` and a non-empty `translation` is `Available: true` with the text.
  Everything else — `Missing`, a state this build has not measured, `Success` with an empty body — is
  `Available: false` and no error, because that answer *is* the service answering. The decoded struct
  declares exactly `id_str`, `translation` and `translationState`: a struct that spelled the rest of
  the response out would be a second copy of the schema to keep in step.
- `var _ domain.Translator = (*Adapter)(nil)` beside the package's other assertion, for the reason that
  one gives.
